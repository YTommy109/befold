## Review Design

**実装コードを書く前**に、これから入れる変更の設計（何を・どこに置くか）だけを
レビューする。実装後の `/code-review` や `review-swift-code` とは対象が違う。
こちらは書かれたコードではなく、backlog タスクの Implementation Plan または
これから書くつもりの設計文を読む。

### いつ使うか

次のいずれかに当てはまる変更で、実装に着手する前に 1 回だけ回す。

- 新しい状態・述語・表示設定を追加する（絞り込み、トグル、モードなど）
- 既存の値の持ち方を変える（computed → キャッシュ、常駐化、正規化の位置を移す）
- 既存の不変条件・共通経路に手を入れる

小さな局所修正（1 ファイル内で完結し、状態も経路も増やさないもの）には使わない。

**サブタスクに分割した機能では、サブタスクごとに回す。** 親タスクで論点を
列挙しても、それは予告であって実行ではない。実装の設計判断はサブタスク側で
下されるため、親で 1 回では届かない（実例: TASK-315 は 3 サブタスクのうち
315.1 でだけ回し、回さなかった 315.2 / 315.3 から 4 件の bug が出た = TASK-326）。

### 前提

このスキルは実測から作られている（TASK-306）。実装直後にまとめて起票された
16 件のレビュー指摘を分類したところ、**約 75〜78%（12〜12.5 件）は実装コードを
読まなくても設計文だけから導けた**。以下のチェックリストは、その 12 件が
どの問いで拾えたかを型にしたもの。

逆に、以下は設計レビューでは出ないので実装後レビューに任せる。

- 既存コードに元からある無駄（差分の設計からは見えない）
- テストコードそのものの書き方（フィクスチャ・寿命・環境依存）
- 実装後に grep して初めて分かる同期漏れ（コメントの列挙ずれなど）

2 度目の実測（TASK-326）でも比率は再現した。TASK-315（git 差分表示）の実装後
レビューで確定した bug 7 件のうち **5 件（71%）は設計文の突き合わせで導ける型**
だった。項目 8・9 と、項目 1・3・6 の拡張は、この 7 件から型を起こしたもの。
このとき効いた教訓は「チェック項目が足りなかった」より
**「決めたことを守らせるものが無かった」**で、次の 3 つはいずれも
判断そのものは正しく記録されていながら担保が無く破れた。

- 申し送りが「着地時の一致確認」だけを指示し、開始時の無効化が抜けた（TASK-317）
- 「粒度はアプリ全体」と決めて doc コメントに書いたが配線されなかった（TASK-319）
- 「列挙式の比較は漏れる」と書いて 1 箇所を直し、兄弟箇所を残した（TASK-320）

### チェックリスト

各項目について「該当しない」で済ませず、**どう該当しないかを 1 行で書く**。
該当するものが見つかったら、実装前に設計を直すか、別タスクとして起票する。

1. **判定の真実の源**
   新しい述語や縮退（機能を無効化する判定）を、データの**中身の有無・形**で
   決めていないか。「空だから安全」は、未変更・未到着・取得失敗でも同じ空に
   なるため破れる。事実（リポジトリを解決できたか等）で判定しているか。
   接頭辞や区切り文字で構造を判定する場合、**同じ形がデータ側にも現れないか**を
   問う。文脈（いま hunk の内か外か等）が要る判定を、行単位のパターン一致だけで
   決めていないか（実例: unified diff のハイフン 3 個 + 空白をハンク内でも
   ファイルヘッダと誤認し、ハイフン 2 個 + 空白で始まる削除行が消えた
   = TASK-316）。

2. **既存の不変条件との衝突**
   その変更は、既存の不変条件（「開いている文書は必ず一覧に含める」等）を
   迂回しないか。新しい述語をどの層に置くかで、不変条件の外側に出てしまう
   ことがある。

3. **消費経路と兄弟判断の全列挙**
   新設した設定・変換・正規化を必要とする消費側を**全部**挙げたか。
   1 箇所に足して満足していないか。指摘された経路を直すのではなく、
   全経路が通る絞り込み点で直せないか。

   同じことを、**同種の判断をしている兄弟箇所**についても問う。再描画の要否・
   キャッシュの再利用可否・追記の可否のように「この状態は変わったか」を判定する
   場所は複数あるのが普通で、片方だけ直すと予告どおりの穴が残る（実例: 再描画
   判定をミラー全体比較へ単純化したが、同じ判断をする `canConsumePendingAppend`
   は列挙式のまま残り、差分トグルが 1 サイクル失われた = TASK-320）。
   構造やクラス名で対象を探す処理（DOM セレクタ・パス一致・型判定）も同様に、
   **新しく増えた対象が既存セレクタに引っかからないか**を `rg` で列挙して確かめる
   （実例: 追記先を `table.code-table` で探す処理が差分テーブルにも一致した
   = TASK-318）。

4. **新しい状態に対応する表示**
   その変更で新しく起こりうる状態（絞り込みで 0 件、取得失敗など）に、
   ユーザーへ出す表示・文言が用意されているか。既存の空状態を流用すると
   事実と食い違うことがある。

5. **ライフサイクル・順序の変化**
   常駐化・キャッシュ化・遅延化で、初期化の前後関係や再計算の回数が
   変わらないか。変わるなら、その順序に依存している既存処理を棚卸ししたか。
   キャッシュにするなら、解決の入力は本当に純粋か（syscall を含まないか）。

6. **高頻度経路のコスト**
   `validateMenuItem`・描画・監視コールバックなど高頻度で走る場所に、
   線形走査や再構築を置いていないか。不可視・非表示のときも仕事を
   続けていないか。**その経路に出てくる呼び出しのうち、実は同期の
   syscall・サブプロセス起動を含むものはないか**（メインアクター外が契約の処理を
   非同期側へ逃がしても、その手前の解決処理が同期のまま残ることがある。
   実例: 差分取得は detached にしたのにリポジトリルート解決だけ MainActor 上の
   `git rev-parse` として残った = TASK-322）。また、表示できない種別のときも
   取得を走らせていないか（実例: 画像・PDF でも毎回 `git diff` = TASK-324）。

7. **測るものと守るものの一致**
   ゲート・プローブ・テストの前提が、守りたい対象と**同じ API・同じ性質**を
   測っているか。条件付きでアサートを飛ばす場合、飛ばしたことが記録に残るか。

8. **非同期で置き換わる表示状態の世代管理**
   非同期取得の結果で表示を差し替える状態には、**開始時の無効化**と
   **着地時の一致確認**の両方があるか。片方だけでは破れる。

   - 開始時に古い値をクリアしないと、対象が切り替わった直後から結果が届くまで
     **前の対象の値が新しい対象の内容として表示される**（実例: TASK-317）
   - 着地時に対象の一致を確認しないと、遅れて届いた結果が現在の表示を壊す

   走行中の要求へ相乗り（合流・デバウンス）させる設計なら、**その要求がいつの
   入力を読んだか**を問う。相乗り先が変更前の状態を読んでいれば、返るのは
   古い結果であり、再取得の手当てが要る（実例: 2 回保存すると 1 回目の差分で
   止まる = TASK-321）。

9. **決めた粒度・共有範囲を守らせるもの**
   「アプリ全体で共有」「ウィンドウごと」「ファイルごと」のような粒度を決めたら、
   **それが破れたときに落ちるもの**（テストか、破れない構造）まで用意したか。
   doc コメントに書いただけでは守られない。特に、共有すべき依存に
   デフォルト引数を持たせると、渡し忘れが**コンパイルエラーにならず**
   静かに別インスタンスになる（実例: `DiffDisplayPreference` がアプリ全体共有の
   設計なのに窓ごとに生成され、2 窓でトグルが同期しなかった = TASK-319）。

10. **型グループの行数と責務の増分**
    この変更で触る型グループ（`Foo.swift` + 同ディレクトリの `Foo+*.swift` の合算）の
    **現行行数を実測し**、追加後の見積もりを書く。

    ```bash
    scripts/check-type-group-size.sh | grep -F '<グループキー>'
    ```

    その上で、責務が増えるかを次の 3 つで具体的に答える。増えるなら**受け皿をどこに
    するか**を実装前に決める（既存の凝集単位へ委譲するか、新しい型を立てるか）。

    - プロトコル準拠が増えるか（実例: `ViewerWindowController` は 5 プロトコルを兼ねていた
      = TASK-411）
    - 親→子へ注入するクロージャが 3 つを超えるか（超えたら delegate プロトコルを検討、
      という既存規定が `docs/dev/rules/product-code.md` の責務分離節にある）
    - stored property が増えるか。増えるならそれは既存の関心に属するか、新しい関心か

    **「extension へ切るから大丈夫」は答えにならない。** 判定は合算なので extension を
    切っても数値は減らず、責務も分かれない（TASK-411 の +Capabilities / +Diff /
    +WindowHelpers が、行数上限の回避であって責務分離ではなかった実例）。
    判断に迷う場合は `responsibility-reviewer` サブエージェントを回す。

### 出力

指摘は「どのチェック項目か・設計のどこが該当するか・実装前に何を決めるか」の
3 点で書く。実装方針を変えるべきものと、別タスクに切り出すものを分けて示す。
結論はタスクの Implementation Plan へ反映する（`backlog task edit <ID> --plan`）。

レビュー結果をユーザーへ提示するときは、`.claude/CLAUDE.md` の
「設計・方針を提示するときは前提と裏付けを明示する」に従い、依拠した前提と
その裏付け（実測 / コード参照 / ドキュメント参照）、裏付けが取れていない前提を
併記する。上のチェックリストの各項目は、まさに**前提が正しいか**を問うている。
