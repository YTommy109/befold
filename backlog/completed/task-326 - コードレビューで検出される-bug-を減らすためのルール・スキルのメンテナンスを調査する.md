### 決定的な 3 つの事例（いずれも記録自体は正しく、担保が抜けた）

1. **TASK-317**: 315.1 の申し送りが「着地時に URL 一致を確認して世代競合を防ぐこと」と指示し、315.3 は実装した（guard fileURL == url）。しかし**裏側の「開始時の無効化」**が抜けた。非同期の世代管理は 2 方向あるのに片方だけを担保した。
2. **TASK-319**: 親 315 の論点に「差分表示の状態をどこに持つか（per-file / ウィンドウ / アプリ全体）」があり、315.3 は「粒度はアプリ全体」と決めて doc コメントにも書いたが、**配線されたことを確かめるものが無かった**。決定が実装で守られていることを破ると落ちるテストが無い。
3. **TASK-320**: 315.3 の Notes 自身が「列挙式の比較だとミラーへフィールドを足したとき判定側が漏れて『状態は変わったのに再描画されない』穴が空く」と書き、updateContent 側をミラー全体比較へ単純化した。しかし**同じ判断をする兄弟箇所** canConsumePendingAppend は列挙式のまま残り、予告どおりの穴が空いた。

さらに TASK-315.2 は「入口の列挙漏れ」（_renderSource だけ直して _renderCode を忘れた）をテスト失敗で発見し Notes に記録している。**同型（経路の列挙漏れ）が同一機能内で 3 回**起きている（315.2 の _renderCode / TASK-318 / TASK-320）。

## 適用した編集（2026-08-06）

### .claude/skills/review-design.md
- **項目 1「判定の真実の源」を拡張**: 中身の有無だけでなく『形』でも判定していないかを問う。接頭辞・区切り文字で構造を判定する処理は、同じ形がデータ側に現れないか・文脈が要る判定でないかを確認する（TASK-316 の型）
- **項目 3 を「消費経路と兄弟判断の全列挙」へ拡張**: 消費側に加えて、同種の判断をしている兄弟箇所（再描画要否・キャッシュ再利用可否・追記可否）を列挙する。構造やクラス名で対象を探す処理は、新しく増えた対象が既存セレクタに引っかからないか rg で確かめる（TASK-320 / TASK-318 の型）
- **項目 6「高頻度経路のコスト」を拡張**: その経路の呼び出しに同期 syscall・サブプロセス起動が紛れていないか。表示できない種別でも取得を走らせていないか（TASK-322 / TASK-324 の型）
- **項目 8 を新設「非同期で置き換わる表示状態の世代管理」**: 開始時の無効化と着地時の一致確認の両方が要る。走行中要求への相乗りは『その要求がいつの入力を読んだか』を問う（TASK-317 / TASK-321 の型）
- **項目 9 を新設「決めた粒度・共有範囲を守らせるもの」**: 粒度を決めたら破れたときに落ちるテストか破れない構造まで用意する。共有依存のデフォルト引数は渡し忘れがコンパイルエラーにならない（TASK-319 の型）
- **「いつ使うか」に追記**: サブタスクに分割した機能はサブタスクごとに回す。親での論点列挙は予告であって実行ではない
- **「前提」に 2 度目の実測を追記**: 7 件中 5 件（71%）が設計文から導ける型で、TASK-306 の 75〜78% と再現。効いた教訓は『チェック項目が足りない』より『決めたことを守らせるものが無い』
