## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
code-review high の効率指摘 2 件。どちらも今回の実装が持ち込んだもので、機能は正しいがコストが要らない場所で発生している。

## 1. メニュー検証のたびに O(entries) の走査（ViewerWindowController.swift:83, :765）
isPreviewingFolder は PreviewTargetResolver.resolve を呼び、その中の `entries.first(where: { $0.id == selection })` は URL 比較の線形走査。これを validateMenuItem が 7 つのセレクタ（find/findNext/findPrevious/print/zoomIn/zoomOut/resetZoom）に対してメインスレッドで実行する。数万件のディレクトリ（TASK-265 が対象にした状況）では、メニューを開くたび・キーボードショートカットを叩くたびに全件走査が複数回走る。結果のキャッシュも、selection == nil の早期 return もない。

## 2. 列挙側で捨てられる URL まで作り直している（DirectoryEnumeration.swift:31,35）
sortedContents は sortedFiles → firstSupportedFile → SupportedFileResolver（CLI/QuickLook のオープン経路）と DirectoryLister.containsSupportedFile(in:)（buildEntries がフォルダー行ごとに 1 回呼ぶ）の共通入口。サブフォルダーが 50 個あるディレクトリを開くと 51 回ぶんの URL 再構築（344 件あたり約 0.7ms の実測）が走り、その大半は first(where:) の 1 件を除いて捨てられる。サイドバーの実消費側は FileListEntry.init で再度揃えている。URL がハッシュキーにならない CLI/QuickLook 経路でも払っている。

## 方針
1 は resolve 結果のキャッシュか、フォルダー判定だけの安い経路を用意する。2 は「正規化は列挙の境界に置く」という TASK-268 の判断を見直し、実際にハッシュキーになる場所（FileListEntry.init）に戻すか、消費側が選べる形にする。TASK-268 の Notes に Quick Open も揃うという利点を書いているため、その利得と天秤にかけて判断する。
