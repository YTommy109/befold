## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-346 で合流の判定を「同じ契機のターンで登録されたか」に変えた結果、**ターンをまたいで届いた契機が合流しなくなった**。

旧設計（チケット比較）では、契機 B のチケットが契機 A の取得開始より前に取られていれば、B は A の走行中の取得へ相乗りできた。ターンが分かれていても合流できたということ。新設計ではバッチが登録ターンの終わりに閉じるため、B が次のターンに届くと別の取得になる。

実害の観測: `ViewerWindowControllerDiffTests`「ソース表示へ切り替えたら差分を取り直す」が main の CI で `callCount → 2` を観測した（run 31141164942）。ソース表示への切替と git 状態の反映という、実際に近接して起きる 2 契機で git が 2 回起動している。

正しさの観点では問題ない（契機ごとに読み直すのは仕様で、古い結果を返すよりよい）。問題はコストで、`.git` の書き込みごとに subprocess が増える方向に効く。

検討すべき方向: バッチを閉じるのを「登録ターンの終わり」ではなく「実際にツリーを読み始めた瞬間」にする。現在の実装は取得タスク本体の先頭（detached の読み取り直前）で閉じているが、その本体が走るタイミングと次の契機の到着順が競合する。読み取りクロージャの中で閉じれば、読み始める前に届いた契機は必ず相乗りできる（batches は MainActor 状態のため、ロックで守る小さな箱が要る）。

着手前に `/review-design` を回すこと（既存の不変条件・高頻度経路のコストに触る変更のため）。実装前に、実際にどれだけ起動回数が増えているかを実測すること（現状は CI の 1 例のみで、増加幅を測っていない）。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
2026-08-07 実測（AC#3）: 実際の refreshDiff 経路で git の起動回数を数える一時テストを両ツリーで実行した。

| ツリー | 同じターンに 2 契機 | ターンをまたぐ 2 契機 |
|---|---|---|
| TASK-346 以前（e674e46c） | 1 | 1 |
| 現 main（59e5c96e） | 1 | 2 |

ターンをまたぐ契機で 1 → 2 回（2 倍）。回帰は確定。

計画（バッチを閉じる時点を「取得タスク本体の先頭」から「実際に読み始めた瞬間」へ移す）を実装したが、**効果が無かった**。実測で crossTurn は 2 のまま。

理由: 読み取りは detached タスクで、メインアクターが 1 ターン進む間に別コアで走り出す。つまり「読み始めた瞬間」は登録のほぼ直後であり、ターンをまたいだ契機はほぼ必ずその後に届く。

旧設計が合流できていたのは、**ルート解決の await（detached を 1 往復）を挟んでから取得を登録していた**ため。合流ウィンドウは「取得の登録より前に契機が来たか」で、そのルート解決のホップがウィンドウを広げていた。TASK-346 でルート解決をローダー内へ移し登録を契機と同時にした結果、このウィンドウが消えた。

つまり旧設計の合流は**偶然の副産物**であり、意図的に作られたウィンドウではなかった。同じ効果を取り戻すには明示的な合流ウィンドウ（デバウンス）が要る。実装は破棄し、方針をユーザーに確認する。

2026-08-07 判断: **対処しない**（ユーザー判断）。

理由:
- 増加は「1 契機あたり」ではなく「近接した 2 契機のときに 1 回増える」に留まる
- 明示的なデバウンスは差分が出るまでのレイテンシを確実に悪化させる一方、改善すべき実害（体感・CPU・サブプロセス数）がまだ測れていない
- 「固定間隔の性能計測は結論が逆転する」の教訓どおり、体感はレイテンシで測るべきで、その計測なしにデバウンスを入れるのは筋が悪い

**見直す条件**: 次のいずれかが観測されたら再開する。
- 保存のたびに体感で差分表示が遅れる、または CPU 使用が目に見えて増える
- `git` のサブプロセス数が問題になる規模（大きなリポジトリ・多数のウィンドウ）で実害が出る
- 契機の数がさらに増える変更を入れるとき（増加が線形に効く）

再開する場合の選択肢は次の 2 つ。どちらも着手前に体感レイテンシの計測を先に行うこと。
1. 明示的な合流ウィンドウ（デバウンス）を入れる
2. 契機側を減らす（setSourceMode = ViewerWindowController.swift:677 と gitStatusDidApply = :521 が近接して両方 refreshDiff を呼ぶ経路の整理）。ただし TASK-330 が「片方にしか届かない」を潰した経緯があるため慎重に扱う。
