## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-315 のコードレビュー（/code-review high・CONFIRMED）で検出。

GitDiffLoader.swift:22 の in-flight 合流は、作業ツリーが変化した後に来た新しい要求を、変化前に開始済みのタスクへ相乗りさせる。短時間に 2 回保存すると、2 回目のリロードの refreshDiff は 1 回目の保存時点のツリーを読んだタスクを await して返し、その後の再フェッチも無効化もないため、表示は 1 回目の保存の差分のまま次のファイルイベントまで止まる。「保存したのに古い差分が出る」という、型の doc コメントが避けると謳っている失敗そのもの。

修正方針の候補: 要求に世代（リクエスト時刻や contentRevision）を持たせ、実行中タスクの開始が要求より古い場合は完了後に再フェッチする、または in-flight 合流をやめて最後の要求だけ生かす（デバウンス + 最新優先）。

関連: GitDiffLoader をウィンドウ間で共有する cleanup タスク（同ファイルの構造に触るため、まとめて実施すると効率的）。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
## 単純化の検討（実装前）

「相乗りをやめて毎回取り直す」案は、二重起動の抑止という型の存在理由を捨てることになる。逆に「世代を持たせて完了後に再取得」案は状態が増える。採ったのは中間で、**要求の到着と取得の開始に共通の通し番号（ticket）を振り、走行中の取得へは『自分より後に始まったもの』にだけ相乗りする**形。追加した状態は単調増加カウンタ 1 つで、判定は `running.ticket > requestTicket` の 1 行に収まる。

結果として重なった要求は「走行中の完了 → 1 回だけ取り直し → 全員がその結果を共有」となり、鮮度と二重起動抑止の両方が立つ（git が同時に 2 つ走ることはない）。

## 実装で踏んだ罠（記録）

最初の実装は開始側が `await` から戻った後に登録を取り下げる形だったため、待機側が先に再開すると完了済みの登録を見つけて待ち直し続け、**メインアクターを空転で占有して `swift test` が終わらなくなった**（600 秒でタイムアウト）。登録の取り下げを「タスク自身が完了前に行う」形へ移して解消した。doc コメントにこの理由を残している。

## 検証

- `swift test` 1150 green
- **テストが空振りしていないことを確認**: 相乗り条件を元の無条件（`return await running.task.value`）へ戻すと、新規・改訂の 2 件だけが落ちる（`(reader.calls → 1) == 2`、`(results[1] → .diff("旧")) == .diff("新")`）。戻して再度 green
- テストは既存の「走行中の要求が重なったら 1 回に畳まれる」を実態に合わせて改訂し（重なり 3 件 → git 実行 2 回）、鮮度を見る「走行中に届いた要求へは、走行後に取り直した新しい結果を返す」を追加した。後者のために、呼ばれるたびに次の結果を返す SequenceDiffReader を足している
- swiftformat --lint: 0 件 / swiftlint: 変更 2 ファイルとも main とのベースライン差分ゼロ
- 全体実行が 2 回連続でハングしたが、sample のスタックは AppKit の NSAnimation 待ちで本変更と無関係。kill 後の再実行は 18.7 秒で 1150 green（TASK-327 に記録）
