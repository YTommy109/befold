## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
2026-08-01 のテストコード全体レビュー(TASK-242〜251 の起票元)で、既存のテスト規約(docs/dev/coding_rule.md L512-771)に明文化されていなかったルールが 6 件顕在化した。同種の問題の再発を規約側で防ぐ。
追記する 6 件:
1. @Suite(.serialized) は根拠コメント必須とし、直列化が必要な最小スイートに限定する(資源基準線を読むテストだけ別スイートへ分割する。実例: GitCommandRunnerTests / FileWatcherIntegrationTests)
2. 待機ループは必ず上限つきにする(while + Task.yield の自作 busy-yield は上限なしだと回帰時に CI をタイムアウト上限まで占有する。waitUntil 系の Issue.record 付きヘルパーを使う)
3. テストフィクスチャは検証に必要な最小サイズにし、サイズの根拠(どの閾値に対する余裕か)をコメントで書く。繰り返し使う大きなフィクスチャは static let で 1 回生成に共有する(TSan 計装下では生成コストが数倍になる)
4. モデル状態のみを検証するテストで実 UI(NSWindow + WKWebView)をフル構築しない(TASK-242 のシーム導入後に、確定したシーム名で記述する。242 完了前に着手する場合はこの項目のみ保留し notes に残す)
5. @MainActor スイートは隔離が必要なテストに限定する。static 純関数のテストは非 MainActor スイートへ置き、並列レーンで走らせる
6. 否定検証(観測しない・発火しない)は固定タイムアウト待ちではなく、番兵(sentinel)で肯定的に配送完了を確認してから未観測を検証する(実例: DistributedAckWaiterIntegrationTests の改善方式)
既存の「発火しない検証は時限+0.3s」ルールとの関係(番兵が使える経路では番兵を優先、使えない時限系は +0.3s)も整理して書く。
注意: TASK-253(coding_rule.md の消費者別分割)が先に完了している場合は分割後の testing.md へ追記する。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
レビュー修正ラウンド1: Important-1(番兵方式の限界を明記), E-1(実UIフル構築禁止をUnit/Integration節へ), E-2(競合テストの一般則), E-3(未文書化挙動をAPI側///にも明文化), Minor-1(N合算ルールを非同期コールバックテスト節へ移設し新節はリンクのみに), Minor-2(L643-646のハードコード参照をアンカーリンク+derived-fromディレクティブへ), Minor-3(@MainActor判定基準に境界の目安を追記) を反映。markdownlint-cli2 0 issues。

レビュー指摘により、初版で「番兵方式なら確実に判定できる」と書いていた箇所を修正した。DistributedNotificationCenter は同一 post 内の observer 呼び出し順を規定しないため、番兵の観測は「配送機構が動いた」ことしか担保せず、対象ハンドラの呼び出し完了は別途保証が要る。この限界を落とすと、規約自身が戒めている「壊れていても通ってしまう」劣化を番兵方式が再生産する。窓を閉じる 2 案(先行登録の前提を明示 / 2 段番兵)を併記し、実装(DistributedAckWaiterIntegrationTests)は 2 段番兵を採用している。
また起票時 #4「モデル状態の検証に実 UI をフル構築しない」が初版で落ちていたため復活させた(TSan 実測で否定された #3 フィクスチャ最小化とは異なり、実測で否定された話ではなく TASK-242/246 の主眼そのもの)。競合テストの一般則(各世代のタスクハンドルを個別に掴み、ゲートで確定順序を固定する)と、テストが依存する未文書化挙動を API 側の /// に明文化する項目も追加した。
「N は経路上の全時限を合算する」ルールは、最初に読まれる既存の非同期コールバックテスト節へ移設し、新節からはアンカーリンクと derived-from ディレクティブで参照する形にした(行番号のハードコード参照は将来ズレるため撤去)。
導入文の項目数の明記は、追記のたびにズレが再生産されるため撤去した。

レビュー修正ラウンド2: 2段番兵の実測結果(フル実行6回中4回失敗、単独実行10/10グリーン)を反映。否定検証節を「配送機構の差し替え検討→2段番兵の負荷時コスト増リスク→1段番兵+前提明示+共有既定の待機予算」の順に書き換え、実測節へ「安定性検証はフル実行で確認する」を追記。markdownlint-cli2 0 issues。

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
テストコード全体レビュー(TASK-242〜251)で顕在化した知見を docs/dev/coding_rule.md のテスト規約へ追記した。
追記項目: (1) .serialized は根拠コメント必須・最小スイートに限定し、別スイートは並列実行される落とし穴を明記 (2) 待機ループは上限つきにし超過時 Issue.record で失敗させる (3) 否定検証は番兵で肯定的に確定してから未観測を見る(番兵の限界と窓の閉じ方を含む)。番兵が使えない時限系は N+0.3 秒で N は経路上の全時限を合算 (4) 移設・統合・パラメタライズは元の不変条件を列挙してから行い、可能なら変異テストで確認する (5) @MainActor スイートは隔離が必要なものに限定 (6) モデル状態の検証に実 UI をフル構築しない (7) 競合テストは各世代のハンドルを掴んで順序を固定する (8) 未文書化挙動への依存は API 側の /// に明文化する (9) 実行時間への寄与は着手前に単独実行で実測する。
特に (4) は今回のレビューで 4 件見つかった事故(いずれも落ちるのではなく通ってしまう方向の劣化)を規約化したもの。
