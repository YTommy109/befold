## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-346 で合流の判定を「同じ契機のターンで登録されたか」に変えた結果、**ターンをまたいで届いた契機が合流しなくなった**。

旧設計（チケット比較）では、契機 B のチケットが契機 A の取得開始より前に取られていれば、B は A の走行中の取得へ相乗りできた。ターンが分かれていても合流できたということ。新設計ではバッチが登録ターンの終わりに閉じるため、B が次のターンに届くと別の取得になる。

実害の観測: `ViewerWindowControllerDiffTests`「ソース表示へ切り替えたら差分を取り直す」が main の CI で `callCount → 2` を観測した（run 31141164942）。ソース表示への切替と git 状態の反映という、実際に近接して起きる 2 契機で git が 2 回起動している。

正しさの観点では問題ない（契機ごとに読み直すのは仕様で、古い結果を返すよりよい）。問題はコストで、`.git` の書き込みごとに subprocess が増える方向に効く。

検討すべき方向: バッチを閉じるのを「登録ターンの終わり」ではなく「実際にツリーを読み始めた瞬間」にする。現在の実装は取得タスク本体の先頭（detached の読み取り直前）で閉じているが、その本体が走るタイミングと次の契機の到着順が競合する。読み取りクロージャの中で閉じれば、読み始める前に届いた契機は必ず相乗りできる（batches は MainActor 状態のため、ロックで守る小さな箱が要る）。

着手前に `/review-design` を回すこと（既存の不変条件・高頻度経路のコストに触る変更のため）。実装前に、実際にどれだけ起動回数が増えているかを実測すること（現状は CI の 1 例のみで、増加幅を測っていない）。
