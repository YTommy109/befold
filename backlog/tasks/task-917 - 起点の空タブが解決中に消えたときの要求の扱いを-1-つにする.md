## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
スタック #769 のレビューで検出。TASK-912 は続けたドロップで後のファイルが失われる不具合を `retargeted` で直したが、同じ型の穴が残っている。CLAUDE.md の「同型のバグが 2 回目に出たら、個別修正をやめて構造で塞ぐ」に当たるので、個別の guard を足さず、空タブが消えた要求の行き先を 1 箇所で決める。

裏付け（コード参照・実機未確認）:
1. `DocumentOpener.openViewer(for:focusesContent:)` は空タブの窓を起点に渡す。解決中に利用者がそのタブを閉じると `containsOpenWindow` で nil が返り、Quick Open や Open Recent で選んだファイルが何も言わず開かれない。TASK-911 以前は起点なしだったので常に開いていた。置き換えた文書タブが閉じて `replacement` が nil になった場合も同じ。
2. `presentOpenPanel` の `guard !blank.isClosed` は `panel.begin` の非モーダルな間に空タブが置き換わると選択を捨てる。TASK-910/911 でサイドバーと Quick Open からも置き換わるようになった。`retargeted` が処理できるのに、手前で落としている。
3. `retargeted` の読み替えは常に `.newTab` なので、`select` が false になる。続けて Open Recent を選ぶと最後に選んだ文書が背面に開き、`focusContentSurface` は見えていないタブへ当たる。
4. `BlankTabWindowController.performFileSwitch` と `fileListDidRequestOpenElsewhere` は同期の `ViewerWindowManager.openViewer` を直接呼ぶので `retargeted` も `containsOpenWindow` も通らない。`fileListDidSelectFile` は `DispatchQueue.main.async` を挟むので、2 つの選択が続いてコントローラがまだ生きていると、閉じた窓のタブとして開こうとする。実際にコントローラが生き残るかは未確認。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
方針: 起点が要求の後に消えたときの行き先を ViewerWindowOpenPolicy.resolveOrigin の 1 箇所で決め、ViewerWindowManager.openViewer の入口で全経路に掛ける（DocumentOpener の retargeted と containsOpenWindow の判定、presentOpenPanel の isClosed の判定は撤去）。置き換え済みなら置き換え先の直後の新しいタブ（元が置き換えの要求なら手前に出す）、閉じていれば起点なしで開く（新しい窓・スライドの要求は種類を保つ）。befold の窓（ViewerDocumentWindow）だけを判定する。
既存テストの変更: 『解決中に閉じた空タブへのドロップは何も開かない』を『起点なしで開く』に書き換えた。要求を捨てない規則への統一による意図した変更。
『最後に選んだ文書が手前』は、解決の早い順に開くと成り立たないので、空タブを起点にする要求（UI からのオープン・ドロップ・パネル）を選んだ順に並べた。起点が文書タブなら待たない。
code-review high: 新しい窓・スライドの要求が化ける、読み替えたタブが末尾に開く、⌘ クリックのタブが手前に出る、直列化が全経路を止める、一括オープンが順序の外にある、テストの確認が空振りする、を直した。見送り: パネルの表示中に空タブを閉じ、選んだファイルが別の窓で開いていると、一括の残りがその窓のタブになる（条件が重なる稀な経路）。ファイル選択パネルそのものを自動テストで操作する手段が無いので、AC #2 はパネルが呼ぶ openInTabs の経路で測っている。
実測: 手前に出す判定・閉じた起点の判定・置き場所のそれぞれを外すと対応するテストが落ちる。swift test 2007 件 + PDF 103 件成功、xcodebuild 成功、swiftlint 新規 0 件。
