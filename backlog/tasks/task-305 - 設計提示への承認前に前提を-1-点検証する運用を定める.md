## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
セッション実測（behold/befold の transcript 3,086 メッセージ）で、ユーザーの発話の 14.1% が「はい」等の承認のみだった。一方、ユーザーが実際に価値を出している指摘 91 件の大半は、コードの誤りではなく AI が置いた前提の誤りの否定だった（例:「タグが指すコミットの総コミット数は規約ではありません」「それはフィーチャーゲートで止めてる機能のはずです」「生成されたテキストファイルなのに NUL が入っているのがおかしいのでは」）。

つまり前提の検査はユーザーの介入によってのみ行われており、「はい」で通した設計提示は前提が未検査のまま実装へ進む。メモリに残る事故（verify-spec-premises-before-starting / degrade-on-facts-not-empty-data / passing-regression-test-only-fixes-assumed-order）はいずれもこの経路で発生している。

AI 側が設計提示時に「この提案が依存している検証可能な前提」を明示し、その根拠を先に示す運用へ変えることで、承認が実質的な検査になるようにする。
<!-- SECTION:DESCRIPTION:END -->

## 実施内容

### AC#1 / #2 規定（.claude/CLAUDE.md）

「設計・方針を提示するときは前提と裏付けを明示する」節を新設した。

- 依拠する検証可能な前提を明示し、前提ごとに裏付けの種類を併記する。種類は実測（実行したコマンドと結果）／コード参照（file_path:line）／ドキュメント参照（spec・ADR・project.yml のコメント等）の 3 つで、どれに当たるか読んで分かる形で書く（AC#1）
- 裏付けが取れていない前提は落とさずに書き、未確認であることと確認方法を明記する（AC#2）
- 実測根拠（transcript 3,086 メッセージ、承認のみ 14.1%、指摘 91 件の大半が前提の誤りの否定）を節内に記載した

TASK-306 で新設した .claude/skills/review-design.md の「出力」節からもこの規定へ導線を張った（チェックリストの各項目はまさに前提の妥当性を問うている）。

### AC#3 メモリとの重複回避・参照関係

- 新規メモリ state-premises-with-evidence-when-proposing.md を作成し、MEMORY.md にポインタを追加
- 既存の verify-spec-premises-before-starting.md に相互リンクを追記
- 役割分担を両方に明記して重複を避けた: 既存メモリは『着手前に入力ドキュメント（spec 等）の前提が実コードとずれていないか確かめる』、新規は『確かめた結果を提示するときに前提と裏付けを併記する』。順序は「入力の前提を確かめる → 提示時に前提と裏付けを書く」。CLAUDE.md の節にも同じ切り分けを書いた
