## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
セッション実測（behold/befold の transcript 3,086 メッセージ）で、ユーザーの発話の 14.1% が「はい」等の承認のみだった。一方、ユーザーが実際に価値を出している指摘 91 件の大半は、コードの誤りではなく AI が置いた前提の誤りの否定だった（例:「タグが指すコミットの総コミット数は規約ではありません」「それはフィーチャーゲートで止めてる機能のはずです」「生成されたテキストファイルなのに NUL が入っているのがおかしいのでは」）。

つまり前提の検査はユーザーの介入によってのみ行われており、「はい」で通した設計提示は前提が未検査のまま実装へ進む。メモリに残る事故（verify-spec-premises-before-starting / degrade-on-facts-not-empty-data / passing-regression-test-only-fixes-assumed-order）はいずれもこの経路で発生している。

AI 側が設計提示時に「この提案が依存している検証可能な前提」を明示し、その根拠を先に示す運用へ変えることで、承認が実質的な検査になるようにする。
<!-- SECTION:DESCRIPTION:END -->
