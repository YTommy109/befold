## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
ダッシュボードのトップに埋め込まれている「最新イベント（直近 20 件）」を別ページへ切り出し、100 件ずつページングで過去へ遡れるようにする。

## 現状（実測）

- 表示は `site/src/views/dashboard.tsx:372-392`。列は 時刻(JST) / 種別 / バージョン / 国 / OS で、`<tbody id="recent-body">` に `summary.recent.map(...)` を流している。
- データ取得は `site/src/analytics.ts:342-353` の `recentEvents(db, afterId = 0)`。`SELECT ... FROM events WHERE id > ? AND ${HUMAN_ONLY} ORDER BY id DESC LIMIT ?` で、`RECENT_LIMIT = 20`（同 `:121`）。
- **過去へ遡る手段が無い。** `afterId` は「その id より新しい」方向の絞り込みで、SSE の差分追記（`eventsAfter`、`analytics.ts:454-465`、`STREAM_LIMIT = 100`）と同じ向き。オフセットもカーソルも持っていない。
- ルーティングは `site/src/index.ts:41` の `app.route('/dashboard', dashboardRoutes)`（`/admin` ではない）。`GET /dashboard`（`site/src/routes/dashboard.tsx:74-78`）と `GET /dashboard/stream`（同 `:80-139`）の 2 本で、どちらもクエリパラメータを受けない。認可は Cloudflare Access JWT のミドルウェア（同 `:42-72`）。
- 本番 D1 の総イベント数は 538 件（2026-08-16 時点、初回 2026-07-29）。100 件ずつなら現状 6 ページ程度。

## 設計上の論点

- **トップに一覧を残すか。** 別ページへ「全部」移すと、トップを開いた瞬間に直近の動きが見えなくなる。トップには短い一覧（現状の 20 件）を残して「もっと見る」で専用ページへ送るか、完全に移すかを決める。SSE によるライブ追記（`recent-body` への差分追記）がトップの機能なので、この判断は SSE の扱いと連動する。
- **専用ページで SSE を動かすか。** 過去ページを見ている最中に新着が先頭へ挿入されると位置がずれる。1 ページ目のみライブ、2 ページ目以降は固定、などの方針を決める。
- **ページングの方式。** `OFFSET` は挿入で境界がずれる。`id` によるカーソル（`WHERE id < ?`）なら安定する。`recentEvents` は SSE と共有されている関数なので、向きの違う 2 つの用途を 1 関数に押し込まず、どこで分けるかを決める。
- **ボット行の扱い。** 現在の一覧は `HUMAN_ONLY` で人間のみ。専用ページでは切り替えられると調査に使えるが、指標側の集約点（`site/src/analytics.ts` の `HUMAN_ONLY`）を壊さないこと。ボット除外条件が 1 箇所に集約されていることは規約テスト `site/test/analytics.test.ts:299` が担保している。

## 注意

- 認可を落とさない。新しいルートも `dashboardRoutes` 配下に置き、Access JWT のミドルウェアを必ず通す（`site/src/routes/dashboard.tsx:42-72`）。旧ホストからのアクセスは 404 のまま。
- 経路（ルート・関数）を増やす変更のため、実装着手前に `/review-design` を 1 回回す。

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. 面を 1 つ足す: DASHBOARD_PAGES に { key: 'events', path: '/events', title: 'イベント' } を追加。ルート生成・ナビゲーション・クエリ本数テストの列挙はこの配列を共有しているので、書き写す場所は増えない（RENDERERS / SUMMARIZERS は Record 型なので書き忘れると型で落ちる）。
2. ページング関数 eventPage(db, cursor?) を analytics.ts に追加。RECENT_COLUMNS と HUMAN_ONLY を共有し、SELECT 句は書き写さない。カーソルは id（OFFSET は使わない）。
   - cursor 無し / {direction:'older', id}: WHERE id < ? ORDER BY id DESC LIMIT N+1
   - {direction:'newer', id}: WHERE id > ? ORDER BY id ASC LIMIT N+1 → 反転
   - N+1 件目の有無で「さらに先があるか」を確定させる（追加クエリ 0 本、1 面 1 本）。
   - 逆向きのカーソルは「そこから来た」ことで存在が確定する（older 遷移なら newer は必ずある）。
3. recentEvents は概要面の 20 件専用のまま触らない。SSE（eventsAfter）とも分ける。
4. ビュー EventsSections（views/dashboard.tsx）: 概要面と同じ 6 列のテーブル + 前後リンク。DashboardPageShell に lastId を渡さず SSE 非接続（スナップショット表示）。
5. 概要面の「最新イベント」見出し横に /dashboard/events への導線を足す。トップの 20 件 + SSE ライブ追記はそのまま残す。
6. ボット行は HUMAN_ONLY のまま（切り替えは入れない。集約点を壊さない）。
7. テスト: analytics.test.ts にページング（先頭・中間・最終・0 件・重複と取りこぼしが無いこと）、dashboard.test.ts に /dashboard/events の 200 と未認証 401/403、query-count.test.ts に events 面を追加。

## /review-design の結果（実装前）

- 項目1・4（判定の真実の源／新しい状態の表示）: 「さらに古いページがあるか」は LIMIT N+1 の実件数で確定させる（追加クエリ 0 本）。一方**「より新しいページがあるか」を older 遷移の履歴から推定する部分は事実判定ではない**。UI が出すカーソルは必ず表示済みの行の id なので実運用では成立するが、URL 手打ち（?before=1 等）では空ページが出うる。→ 0 件表示（「該当するイベントはありません」）を必ず用意し、空でも壊れない形にする。
- 項目2（既存の不変条件）: RECENT_COLUMNS の doc コメントが「recentEvents と eventsAfter で共有」と 2 関数を列挙している（analytics.ts:813-822）。3 つ目を足すので**文言を同期する**（列挙式の同期漏れ型）。HUMAN_ONLY は定数を使い、集約点の規約テストを壊さない。
- 項目3（消費経路の全列挙）: 実測 grep で DASHBOARD_PAGES の消費側は analytics.ts / views(Nav) / routes(RENDERERS) / query-count.test / dashboard.test の 5 箇所、いずれも配列を列挙して回すか Record 型で強制される。面を足せばルート・認可（401/403/404）・ナビ・クエリ本数の各テストが自動で付く（AC#4 はこれで担保される）。Cloudflare Access は `/dashboard/*` のアプリが覆うためインフラ変更は不要（site/README.md:596-598）。**列挙駆動でない唯一の場所は README のルート表**なので 1 行足す。
- 項目6（高頻度経路のコスト）: HUMAN_ONLY で絞るため LIMIT 101 を満たすまでの主キー走査量はボット比率に依存する。本番 538 件規模では無視できる。将来ボットが大半になったときに効くことを Notes に残す。
- 項目7（測るものと守るもの）: AC#3 は「先頭から最終ページまで順に辿って集めた id 集合が、全人間行と過不足なく一致し重複が無い」テストで測る（リンクを 1 本ずつ検証する形にしない）。1 ページ 100 件であることも実測して固定する（RECENT_LIMIT 20 と別定数にした判断が破れたら落ちる）。
- 項目5・8（ライフサイクル／非同期の世代管理）: 該当しない。イベント面はサーバ側レンダリングのみで SSE にも JS にも接続しない。
- 項目9（粒度を守らせるもの）: 「イベント面はライブ更新しない」は lastId を渡さないことで表現され、既存テスト「ライブ更新しない面には SSE の状態表示を出さない」に events を加えて固定する。
- 項目10: Swift 固有のため該当しない（site の TypeScript 変更）。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
## 実装した形

- 面を 1 つ足した: `DASHBOARD_PAGES` に `{ key: 'events', path: '/events', title: 'イベント' }`。ルート・ナビ・認可（401/403/404）・クエリ本数の各テストは配列を列挙して回るので自動で events を含む。`RENDERERS` / `SUMMARIZERS` は `Record<DashboardPageKey, ...>` なので、書き忘れは型で落ちた（実測: 追加直後の `tsc` が query-count.test.ts の SUMMARIZERS で TS2741）。
- `eventPage(db, cursor?)`（analytics.ts）: `WHERE id < ?`（older）/ `id > ?`（newer, 昇順で引いて反転）。SELECT 句は `RECENT_COLUMNS`、ボット除外は `HUMAN_ONLY` を共有。**上限より 1 件多く引いて「次のページがあるか」を同じクエリで確定**させる（1 面 1 本のまま。合計は 16 → 17 本）。
- `parseEventCursor`: `Number` + `Math.trunc`、空文字・負値・数値でない値は基準無し（最新ページ）へ倒す。`before` と `after` が同時なら `before` を採る。

## 判断の記録（AC #5）

- **トップの一覧と SSE はそのまま残した。** 概要面の直近 20 件とライブ追記は「いま何が起きているか」を見るための機能で、全部をイベント面へ移すとトップを開いた瞬間に動きが見えなくなる。見出しの下に `/dashboard/events` への導線を足すだけにした。
- **イベント面は SSE に接続しない。** 過去を見ている最中に先頭へ行が挿し込まれると読んでいる位置がずれる。`DashboardPageShell` に `lastId` を渡さないことで表現し、既存テスト「ライブ更新しない面には SSE の状態表示を出さない」へ events を加えて固定した。
- **ボット行の切り替えは入れていない。** `HUMAN_ONLY` の集約点を壊さない判断（規約テスト「自動アクセス除外の条件が 1 箇所に集約されている」が担保）。調査用に切り替えたくなったら別タスク。
- **`RECENT_LIMIT`(20) と `EVENTS_PAGE_LIMIT`(100) は別定数。** 片方を変えたときにもう片方が動かないようにした。1 ページ 100 件であることはテストで実測している。
- **`OFFSET` は使わない。** イベントは常に新しい側へ挿入されるため、オフセットではページ送りの途中で境界がずれる。

## 実測

- `npx vitest run`（site）: 12 ファイル 337 件すべて通過。`npx tsc --noEmit`: 出力なし。`npm run lint` / `npm run format`: 指摘なし。`markdownlint-cli2`: 0 issues。
- **テストが退行を捉えることを確認した**（修正を戻して落ちることの確認）。境界を `id <` → `id <=` に壊すと 3 件（最終ページ・全件走破・新着中の境界）が落ち、「次のページの有無」を件数ではなくカーソルの有無で決める形に戻すと 1 件（最終ページ）が落ちた。どちらも元に戻して全通過を再確認済み。
- 自分の doc コメントに `FROM events` と書いたせいで規約テストが偽陽性で落ちた（窓が `${HUMAN_ONLY}` を含まない）。文言を変えて解消。この構造ガードは「コメント中の同じ語」にも反応する。

## 残した制約

- HUMAN_ONLY で絞るため、LIMIT 101 を満たすまでの主キー走査量はボット比率に依存する。本番 538 件規模（2026-08-16 時点）では無視できる。ボットが大半を占める規模になったら、`events` に部分インデックスを足すか判定列を持たせる検討が要る。
