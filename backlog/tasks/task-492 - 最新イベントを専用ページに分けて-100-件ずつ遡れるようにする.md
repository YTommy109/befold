## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
ダッシュボードのトップに埋め込まれている「最新イベント（直近 20 件）」を別ページへ切り出し、100 件ずつページングで過去へ遡れるようにする。

## 現状（実測）

- 表示は `site/src/views/dashboard.tsx:372-392`。列は 時刻(JST) / 種別 / バージョン / 国 / OS で、`<tbody id="recent-body">` に `summary.recent.map(...)` を流している。
- データ取得は `site/src/analytics.ts:342-353` の `recentEvents(db, afterId = 0)`。`SELECT ... FROM events WHERE id > ? AND ${HUMAN_ONLY} ORDER BY id DESC LIMIT ?` で、`RECENT_LIMIT = 20`（同 `:121`）。
- **過去へ遡る手段が無い。** `afterId` は「その id より新しい」方向の絞り込みで、SSE の差分追記（`eventsAfter`、`analytics.ts:454-465`、`STREAM_LIMIT = 100`）と同じ向き。オフセットもカーソルも持っていない。
- ルーティングは `site/src/index.ts:41` の `app.route('/dashboard', dashboardRoutes)`（`/admin` ではない）。`GET /dashboard`（`site/src/routes/dashboard.tsx:74-78`）と `GET /dashboard/stream`（同 `:80-139`）の 2 本で、どちらもクエリパラメータを受けない。認可は Cloudflare Access JWT のミドルウェア（同 `:42-72`）。
- 本番 D1 の総イベント数は 538 件（2026-08-16 時点、初回 2026-07-29）。100 件ずつなら現状 6 ページ程度。

## 設計上の論点

- **トップに一覧を残すか。** 別ページへ「全部」移すと、トップを開いた瞬間に直近の動きが見えなくなる。トップには短い一覧（現状の 20 件）を残して「もっと見る」で専用ページへ送るか、完全に移すかを決める。SSE によるライブ追記（`recent-body` への差分追記）がトップの機能なので、この判断は SSE の扱いと連動する。
- **専用ページで SSE を動かすか。** 過去ページを見ている最中に新着が先頭へ挿入されると位置がずれる。1 ページ目のみライブ、2 ページ目以降は固定、などの方針を決める。
- **ページングの方式。** `OFFSET` は挿入で境界がずれる。`id` によるカーソル（`WHERE id < ?`）なら安定する。`recentEvents` は SSE と共有されている関数なので、向きの違う 2 つの用途を 1 関数に押し込まず、どこで分けるかを決める。
- **ボット行の扱い。** 現在の一覧は `HUMAN_ONLY` で人間のみ。専用ページでは切り替えられると調査に使えるが、指標側の集約点（`site/src/analytics.ts` の `HUMAN_ONLY`）を壊さないこと。ボット除外条件が 1 箇所に集約されていることは規約テスト `site/test/analytics.test.ts:299` が担保している。

## 注意

- 認可を落とさない。新しいルートも `dashboardRoutes` 配下に置き、Access JWT のミドルウェアを必ず通す（`site/src/routes/dashboard.tsx:42-72`）。旧ホストからのアクセスは 404 のまま。
- 経路（ルート・関数）を増やす変更のため、実装着手前に `/review-design` を 1 回回す。
