閾値が「責務を分けろ」という設計上の圧力として働くのは、余裕があるうちだけ。残り 1〜3 行の状態が常態化すると、次に触った人は**責務と無関係な理由で**（コメントを削る・doc を書かない・テストを別ファイルへ散らす）閾値を回避することになる。TASK-547 では実際に、判断を型の doc コメントとして残そうとしたら 415 行になって書けず、規約文書へ追い出した。

## 決めること

- 10 件それぞれについて「責務で返済できる / できない」を判定する。できないものは恒久例外へ理由つきで登録する（TASK-547 の `MainMenuBuilder` が前例）
- テストターゲットのグループ（`SidebarExpansionTests` / `ViewerStoreChunkTests` / `ViewerBridgeContractTests`）を本番コードと同じ 400 で縛るのが妥当か。テストは網羅を増やすほど太るのが正常で、圧力の向きがプロダクトコードと違う
- 全件を 1 タスクでやるとレビュー不能なので、判定だけを行ってサブタスクへ割るのが現実的

このタスクは「閾値を緩める」ためのものではない。閾値を緩める結論を出す場合は、なぜ 400 が機能していないかを実測で示すこと。

## 命名による閾値の抜け道（実測で発見）

`check-type-group-size.sh` は `base="\${base%%+*}"` で最初の `+` の手前までをグループキーにする。テストで `Foo+BarTests.swift` という名前を使うと、キーが `Foo` になり `FooTests` と**合算されない**。

```
308  BefoldApp/befoldTests/DocumentCommandControllerTests   ← 本体
206  BefoldApp/befoldTests/DocumentCommandController        ← +JumpTests / +OpenBarTests の合算
```

同一対象・同一ヘルパー・同一 fake を共有する 514 行が、命名の形だけで 2 グループに分かれて通っている。`befoldTests/` で `+` を含むファイルはこの 2 本だけ（実測）で、他の分割はすべて別名（`DirectoryLister*Tests` / TASK-431 の 14 スイート）を採っている。

意図的な抜け道ではなく、`Type+Feature.swift` 規約をテスト名にそのまま当てた副作用と見られる。

## AC#2 は「該当 0 件」で満たされる（実測）

**閾値以下のグループには恒久例外を登録できない。** `check-type-group-size.sh` の判定は `else if (lines <= t)` で無条件に「不要な例外」となり exit 2 を返す。実測:

```
$ TYPE_GROUP_EXCEPTIONS=<仮> scripts/check-type-group-size.sh --check
```

`ci.yml:120-128` は exit 2 を `::warning::` にして pass させるので CI は赤くならないが、登録した件数ぶん恒久的な警告が出続ける。

今回「返済不能」と判定したのは `MainMenuBuilder`（399 行）1 件だけで、これは閾値以下のため登録できない。TASK-547 で判断を `docs/dev/rules/product-code.md` の責務分離節へ記録し、「400 行を超えたら分割ではなく恒久例外へ登録する」と明記済み。**したがって今回追加すべき例外エントリは 0 件。**

## AC#3: テストターゲットを本番コードと同じ 400 行で縛るか → **据え置く**

### 判断の経緯（記録の裏取り）

TASK-428.1 で論点として起票され、決定として記録されていた（単に除外しなかったのではない）。

> 対象範囲: BefoldApp 配下の全 .swift。除外は .swiftlint.yml の excluded と同じ .build / befold/Resources の 2 つのみ。テストターゲットも file_length の対象なので同じ扱いに揃えた

ただし**根拠は「`file_length` が既にテストを対象にしているから揃える」の 1 点のみ**で、テスト固有の性質（セットアップの重複・説明コメントの比重・凝集の単位）は検討されていない。

### 据え置く理由

1. **分布上テストが特別に苦しいわけではない。** 300 行以上の比率はテスト 7.6%（23/302）・プロダクト 6.7%（13/195）でほぼ同じ。371〜399 の張り付き帯はプロダクト 7 件・テスト 3 件で、**むしろプロダクト側の方が余裕がない**。テストだけ緩めるのは苦しい側を放置して楽な側を緩めることになる。
2. **今回の 3 件はいずれも意味のある境界を持つ**（上の表）。閾値の是非を決めなくても正しい行動が確定する。特に `ViewerBridgeContractTests` の共有ヘルパー 130 行は、閾値と無関係に `*TestSupport.swift` へ出すべき歪み（他 3 スイートが `@Suite` 型の static を借りている）。
3. **緩めると `.swiftlint.yml` の `file_length` 400 と食い違う。** TASK-428.1 が物理行数を採った理由（両者で意味を揃える）が崩れる。
4. 行数を理由にした分割の前例が 20 ファイル + TASK-431 の 14 スイートあり、**破綻せずに回っている**（TASK-431 は 66 テストを不変のまま割り、`swift test` 1442 件通過）。

### 据え置きに伴って残る宿題

- 上記の**命名による抜け道**（`DocumentCommandController` 514 行）。閾値を据え置くなら、これを塞ぐか「別型名への切り出しは返済手段なので意図どおり」と明文化するかを決める必要がある。塞ぐ場合はテストの判定を「対象型名で束ねる」形へ変えることになり、`ViewerStore*Tests`（11 ファイル）等の再集計が先に要る。
- **doc コメントを削るのは返済ではない。** 4 グループの doc 比率は 17〜47%（`ZoomingPDFView` は 185/392 = 47%）。物理行数で数える以上、doc を削れば数字は下がるが、そこに書かれているのは実測と判断であり、規約の「例外行を消すときは理由の行き先を決める」と同じ理由で削ってはならない。次に閾値へ近づいたセッションが最短の手として doc 削りを選ばないよう、ここに明記しておく。
