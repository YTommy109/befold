## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
1 ページに詰め込まれたダッシュボードを目的別のページへ分け、1 回の表示で発行する D1 クエリ本数の上限をページ単位で持てるようにする。

## 現状（実測、2026-08-16）

- **1 ページに 12 セクション。** `site/src/views/dashboard.tsx` の `<h2>` を数えた実測値。累計 / 本日 / 日毎の推移 / 日別のユニークアクセス元 / 時間帯分布 / 内訳 / 稼働中のアプリバージョン / ページ別の訪問 / 言語別の訪問 / 配布ホストと旧経路 / 人間の訪問と自動アクセス / 最新イベント。
- **1 回の表示で 13 クエリ。** `summarize()`（`site/src/analytics.ts:884-937`）が `Promise.all` で発行する。上限は `site/test/query-count.test.ts:44` の `MAX_QUERIES = 13` で、**現在ちょうど満杯**。
- **上限に空きが無いため、指標を足すたびに既存クエリの畳み込みが要る。** 実際 TASK-491.2 は os / as_org の 2 本を `UNION ALL` で 1 本に畳んで枠を空けてから稼働バージョン分布を入れた（経緯は `site/test/query-count.test.ts:6-43` のコメントに履歴として残っている）。TASK-493（アップデートの取り込み）と TASK-495（GitHub フォールバック配信）も同じ壁に当たる。
- **ルーティングは 2 本だけ。** `GET /dashboard` と `GET /dashboard/stream`（`site/src/routes/dashboard.tsx:74-139`）。認可は Cloudflare Access JWT のミドルウェア（同 `:42-72`）。SSE は `summarize()` を再実行して `renderSummarySections()` の HTML で `#summary` を丸ごと置換する（同 `:124-128`）。

## この分割で何が変わるか

`MAX_QUERIES` の目的は性能上限ではなく「**指標を 1 つ足すたびにクエリが 1 本増える**形への退行検知」（TASK-423 で 19 → 13 に畳んだ経緯が上記コメントにある）。ページを分けても、この退行そのものは防げない。**したがって上限テストは撤去せず、ページごとの上限へ作り替える。**

## 決めること

- **ページの切り方。** 12 セクションを何面に分けるか。案: 概要（累計・本日・日毎の推移）/ 利用者（日別ユニーク・稼働バージョン・時間帯）/ 流入（内訳・ページ別・言語別）/ 配信（ホストと旧経路・フォールバック）/ イベント一覧。目的で分けるのか、更新頻度（全期間累計 か 直近 N 日）で分けるのかを決める。
- **SSE をどのページで動かすか。** 現在は `#summary` 全体を置換する 1 本。ページごとに部分置換へ変えるか、ライブ更新はトップだけにするか。
- **`summarize()` を分けるか。** 現在は全指標を 1 関数で取る。ページごとに必要な集計だけを引く形にすると、関数が面の数だけ増える。共通の型（`Summary`）を保ったまま部分取得にするか、面ごとの関数へ割るかを決める。
- **上限テストの作り替え方。** ページごとに `MAX_QUERIES` を持つのか、全ページの合計に上限を置くのか。「面を増やせば上限を回避できる」形になっていないか。
- **ナビゲーション。** 面をまたぐ導線をどう出すか。Cloudflare Access の認可はどの面にも掛かる必要がある。

## 注意

- **認可を落とさない。** 新しいルートも `dashboardRoutes` 配下に置き、Access JWT のミドルウェアを必ず通す（`site/src/routes/dashboard.tsx:42-72`）。
- **ボット除外の集約点を壊さない。** `HUMAN_ONLY` が 1 箇所に集約されていることは規約テスト（`site/test/analytics.test.ts:519-541`）が担保しており、これは `analytics.ts` の**ソース文字列**を検査する形。`site/src/analytics.ts` を複数ファイルへ分割すると、この検査が分割後のファイルに届かなくなる（`site/vitest.config.ts:24` が `analytics.ts` 1 ファイルだけを `TEST_ANALYTICS_SOURCE` として渡している）。集計 SQL の置き場を動かす場合は、検査の対象範囲を同時に直す。
- TASK-492（最新イベントの専用ページ）は、この分割の一部として吸収できる可能性がある。分割の設計時にどちらで扱うかを決める。
- 経路（ルート・関数）を増やす変更のため、実装着手前に `/review-design` を 1 回回す。

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
## ページ構成（ユーザー判断 2026-08-16）

| ルート | 面 | セクション | クエリ |
|---|---|---|---|
| `/dashboard` | 概要 | 累計 / 本日 / 日毎の推移 / 最新イベント | 4 |
| `/dashboard/users` | 利用者 | 日別ユニークアクセス元 / 稼働バージョン / 時間帯分布 | 3 |
| `/dashboard/traffic` | 流入 | 内訳 / ページ別 / 言語別 / 人間と自動アクセス | 8 |
| `/dashboard/delivery` | 配信 | 配布ホストと旧経路 | 1 |

TASK-493 は利用者面、TASK-495 は配信面に載る。

## 決めたこと（/review-design の結果）

### 1. ページの定義元は 1 本の配列にする（項目 1・9）

`DASHBOARD_PAGES` を値として持ち、**ルート生成とテストの両方がこれを読む**。
ページの列挙をルート文字列やファイルの有無で判定しない。レジストリに載せない
ページは存在できないので、テストの列挙から漏れる面が作れない。

### 2. 上限は「ページごと」と「全ページ合計」の 2 段（項目 7・9）

ページごとの上限だけだと、面を増やすことで上限を回避できてしまう。合計上限を
併せて置くことで「指標を 1 つ足すたびにクエリが 1 本増える」形への退行検知
（MAX_QUERIES 本来の目的、TASK-423）を保つ。

### 3. `summarize()` は面ごとの関数へ割り、統合版は撤去する（項目 3）

13 クエリを一度に引く経路を残すと上限テストの意味が薄れる。消費者は
`/dashboard` ハンドラと `/dashboard/stream` の 2 つだけなので、置き換えは閉じる。

### 4. `analytics.ts` は分割しない（項目 2・10）

ボット除外の集約を担保する規約テスト（site/test/analytics.test.ts:519-541）は
`analytics.ts` の**ソース文字列**を検査する形で、`site/vitest.config.ts:24` が
このファイル 1 本だけを `TEST_ANALYTICS_SOURCE` として渡している。分割すると
検査が分割後のファイルへ届かず、AC #5 が破れる。970 行に足すことになるが、
集計 SQL の置き場は 1 ファイルのままにする。

### 5. SSE は概要面だけで動かす（項目 5）

ライブで見たいのは最新イベントと本日の数字で、どちらも概要面にある。他の面は
分析用のスナップショットとして扱う。副次的に、新着ごとの再集計が 13 クエリから
4 クエリへ軽くなる。**非ライブの面には SSE の状態表示を出さない**（出すと
更新されているように読める）。

### 6. 認可は既存のミドルウェアがそのまま効く（項目 2）

`dashboardRoutes.use('*')`（site/src/routes/dashboard.tsx:42）が新ルートにも
掛かる。旧ホストの 404 も同じ。新ルートを `dashboardRoutes` 配下に置く限り
落ちないが、面ごとに 401/403 のテストを置いて担保する。

### 7. 該当しない項目

- 項目 8（非同期で置き換わる表示状態の世代管理）: SSE は単方向 push で、
  置き換えは innerHTML の全置換 1 種類のみ。競合する世代が無い。
- 項目 10（Swift の型グループ行数）: 対象が Swift 専用。JS 側に同等の閾値は無い。

## 実装順

1. `DASHBOARD_PAGES` レジストリと面ごとの summarize を analytics.ts に追加
2. ルートをレジストリから生成し、`/stream` を概要面のセクションへ向ける
3. views を面ごとのセクション群 + 共通シェル（nav 付き）へ組み替える
4. テスト: クエリ本数（ページごと + 合計）、面ごとの表示、面ごとの 401/403、
   レジストリと生成ルートの一致
5. 判断（ページの切り方・SSE の置き場・analytics.ts を分割しない理由）を Notes へ

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
## 実装した形

| ルート | 面 | クエリ（実測） |
|---|---|---|
| `/dashboard` | 概要 | 4 |
| `/dashboard/users` | 利用者 | 3 |
| `/dashboard/traffic` | 流入 | 8 |
| `/dashboard/delivery` | 配信 | 1 |
| | **合計** | **16** |

実測方法: 上限を 0 に落として失敗させ、`expected N to be less than or equal to 0` の
N を読んだ（テストが空振りしていないことの確認を兼ねる）。

## 決めたことと担保

- **面の定義元は `DASHBOARD_PAGES`（analytics.ts）1 本。** ルート生成・
  ナビゲーション・上限テストの列挙がこの配列を共有する。ルート側の `RENDERERS` と
  テスト側の `SUMMARIZERS` はどちらも `Record<DashboardPageKey, ...>` なので、
  面を足して描画やテストを書き忘れると**型で落ちる**。
- **上限は 2 段。** ページごと 8 本と全ページ合計 20 本。ページごとだけだと
  「面を増やせば上限を回避できる」形になるため、合計にも置いた。
- **SSE は概要面だけ。** `lastId` を渡した面だけがストリームに接続する。渡さない面は
  スクリプトも状態表示も出さず、代わりに「開いた時点のスナップショット」と明示する。
  副次的に、新着ごとの再集計が 13 クエリから 4 クエリへ減った。
- **`analytics.ts` は分割しなかった。** ボット除外の集約を担保する規約テスト
  （site/test/analytics.test.ts）が `analytics.ts` のソース文字列を検査する形で、
  `site/vitest.config.ts` がこの 1 ファイルだけを渡している。分割すると検査が
  届かなくなる（AC #5）。

## 分割の過程で見つけて直したもの

- **4 セクション（累計・本日・日毎の推移・時間帯分布）が `perKind` を
  `{kind, label}` としてしか使っていなかった。** 実体は `KIND_LABELS` で足りる。
  `perKind` は指標別内訳クエリの結果なので、これを参照していたために概要面が
  流入面のクエリに依存する形になっていた。`KIND_LABELS` へ差し替え、
  `perKind` を使うのは流入面の「内訳」節だけにした。
- **稼働バージョンの注記が「下の『バージョン別ダウンロード』とは別物」と
  書いていた。** その表は流入面へ移ったので「流入面の」に直した。分割で
  壊れる文言はこれ 1 箇所（`grep '下の\|上の'` で確認）。

## テスト

- `query-count.test.ts`: 面ごと（`it.each`）＋合計＋レジストリ一致の 6 件へ作り替え
- `dashboard.test.ts`: 面ごとの 200/401/403/旧ホスト 404（`it.each` で全面）、
  面間の導線、非ライブ面に SSE 状態表示を出さないこと、を追加。既存の表示テストは
  内容のある面へ向け直した
- `analytics.test.ts`: 集計 SQL の振る舞いを見るテストは面の割り当てと無関係なので、
  4 面の結果を 1 つに畳む `summarizeAll` ヘルパを置いて既存のアサーションを保った

## 変異テスト（空振りしていないことの確認）

- 利用者面に `lastId` を渡す変異 → 「ライブ更新しない面には SSE の状態表示を
  出さない」が落ちる
- 上限を 0 にする変異 → 面ごと 4 件と合計 1 件が落ち、実測値が読める
