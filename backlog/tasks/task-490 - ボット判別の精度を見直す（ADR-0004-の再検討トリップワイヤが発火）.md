## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
データセンター由来の自動アクセスが「人間の訪問」として計上されており、人間の訪問数が実態より膨らんでいる。ADR 0004 が定めた再検討条件を既に満たしているため、判別方式を見直す。

## きっかけ（2026-08-16 の実測）

TASK-489.3 で gh-pages 流入を調べる過程で、参照元に `http://befold.degino.com:2052` `:2086` `:8080` `:8880` という Cloudflare の HTTP 代替ポートが各 1 件現れた。実体を D1 で確認したところ、4 件すべてが接続元組織 **Driftnet Ltd**（インターネット全域スキャン業者）で、`ua_summary` は `other`、`os` は NULL、`kind` は `visit`。**ボット判定に該当せず人間として計上されていた。**

範囲を広げて、人間として計上されている visit を接続元組織別に見た結果（上位）。

| 接続元組織 | ua_summary | 件数 | ユニーク |
| --- | --- | --- | --- |
| Meta Platforms Ireland Limited | other | 54 | 53 |
| Amazon Data Services Northern Virginia | Chrome | 31 | 31 |
| ARTERIA Networks Corp. | Chrome | 28 | 9 |
| Amazon Technologies Inc. | Chrome | 24 | 22 |
| Google LLC | other | 15 | 11 |
| (null) | curl | 14 | 2 |
| SAKURA Internet Inc. | other | 12 | 8 |
| Twitter Inc. | other | 8 | 5 |
| DigitalOcean, LLC | curl 等 | 7 | 5 |
| Driftnet Ltd | other | 6 | 6 |

同時点の human visit 総数は 354 件。Meta / Amazon / Google / Twitter / DigitalOcean / Driftnet といったデータセンター・SNS のリンク展開だけで **150 件規模**あり、人間の訪問数の見え方が大きく変わる。

## ADR 0004 との関係

`docs/adr/0004-bot-detection-via-user-agent.md` は「まず User-Agent のトークン判定でボットを分類する。`cf.botManagement` は使わない」と決めた。その理由は妥当だったが、**前提が変わっている**。

ADR 0004 が挙げた再検討トリップワイヤ（同 :103-110）のうち、次が発火している。

1. **「独自ドメインへ移行する、または Bot Management が使える構成になり、`cf.botManagement` が実際に取得できると実測できたとき」** — 独自ドメインへの移行は TASK-476 / ADR 0007 で完了済み。ADR 0004 執筆時点の前提だった「`workers_dev = true` の独自ドメイン無し運用」（同 :30-33）はもう成り立たない。`cf.botManagement` が取得できるかは当時「未実測」のままなので、まず実測する。
2. **「計測結果を llms.txt の要否判断以外の用途（詐称耐性が要る用途）に使う要件が生まれたとき」** — TASK-489 で、旧ホストと GitHub 配布経路を停止してよいかの判断材料に使う予定。停止判断は取り返しがつかないため、人間の数が膨らんだままだと誤った判断につながる。

## 扱いの方針

ADR 0004 の判断を否定するのではなく、**トリップワイヤが発火したので予定どおり再検討する**という位置づけで進める。UA 判定を捨てるとは限らない（`cf.botManagement` が取得できない、または精度が伴わない可能性がある）。実測してから決めること。

`as_org` による事後検算は ADR 0004 自身が想定していた手段（同 :47-49「UA と ASN の食い違いは事後に検算できる」）なので、`cf.botManagement` が使えない場合でも ASN ベースの分類は選択肢になる。

## AC#1 の実測（2026-08-16）

**結論: 現構成で `request.cf.botManagement` は取得できない。**

1. **実測（エッジ実行）**: 使い捨ての最小 Worker（`export default { fetch(request) { ... } }` が `request.cf` を JSON で返すだけ）を `npx wrangler dev --remote` で Cloudflare のエッジ上に置き、`curl http://127.0.0.1:8799/` で叩いた。返った `Object.keys(request.cf)` は次の 30 個で、`botManagement` は**含まれない**（`request.cf.botManagement` は `undefined`）。

   `asOrganization, asn, city, clientQuicRtt, clientTcpRtt, colo, continent, country, edgeL4, edgeRequestKeepAliveStatus, httpProtocol, isEUCountry, latitude, longitude, postalCode, region, regionCode, requestHeaderNames, requestPriority, timezone, tlsCipher, tlsClientAuth, tlsClientCiphersSha1, tlsClientExtensionsSha1, tlsClientExtensionsSha1Le, tlsClientHelloLength, tlsClientRandom, tlsExportedAuthenticator, tlsVersion, verifiedBotCategory`

   計測後、プローブ Worker は破棄した（`wrangler dev` のプレビューなのでデプロイ資産は残らない）。
2. **契約プランの確認（Cloudflare API）**: `GET /zones` で `degino.com` の plan は `Free Website`。
3. **ドキュメント**: Bot Management Variables は「Requires a Cloudflare Enterprise plan with Bot Management enabled」（developers.cloudflare.com/bots/reference/bot-management-variables/、cf.bot_management.verified_bot のリファレンス）。

つまり ADR 0004 のトリップワイヤ 1 は「独自ドメインへ移行した」という条件は満たしたが、**`cf.botManagement` が取れるようにはならなかった**（必要なのはドメインではなく Enterprise + Bot Management 契約）。発火しているのはトリップワイヤ 3（詐称耐性が要る用途＝TASK-489 の停止判断）のみ。

補足: `cf.verifiedBotCategory` は Free でも **キーとして存在する**。ただし値が入るのは Cloudflare が逆引き検証済みの good bot だけで、今回問題になっている EC2 / Driftnet 等のスキャナは対象外。単体では本タスクの課題を解けない。

## /review-design の結果（実装着手前・2026-08-16）

チェックリスト 10 項目のうち、設計を変えた指摘が 6 件。

1. **判定の真実の源（項目 1）— 設計変更あり。** as_org の部分一致は「文字列の中身」判定なので破れる方向を先に決める。
   - **プライバシー中継をデータセンターに入れない。** iCloud Private Relay / WARP の出口は as_org が Cloudflare / Akamai / Fastly になる。実測でも `Cloudflare London, LLC` + Chrome + macOS + JP が 1 件あり、これは人間の可能性が高い。入れると人間を落とす。同じ理由で TOR EXIT（2 件）と UAB code200（プロキシ業者、5 件）も入れない。
   - **as_org が NULL の 34 件は人間側に残す。** NULL は「データセンターでない」ではなく「不明」（ローカル/テストなど cf が無い経路を含む）。かつ `NULL LIKE ...` は NULL を返すので、素の LIKE を WHERE に置くと BOT_MATCH と同じ「黙って全集計から消える」事故が再現する。`COALESCE(as_org,'')` を必ず噛ませる。
2. **消費経路の全列挙（項目 3）— 設計変更あり。** HUMAN_ONLY 経由の 8 箇所（analytics.ts:219/233/253/279/321/529/555/657）は自動で効く。効かないのは **BOT_MATCH を直接使う 3 箇所**（uaSplit 345-346、uaBreakdown 370、eventBreakdowns 429 の `AS is_bot`）。ここを直さないと、人間側から引かれた分がロボット側にも出ず**総和が合わない**（画面上で件数が消える）。
3. **除外した量が見えなくなる（項目 4）— 設計変更あり。** `metricBreakdown('as_org')`（analytics.ts:555）は HUMAN_ONLY 付きなので、**今回の問題を発見した「接続元組織別」テーブルから当の組織が消える**。データセンター専用の内訳表を必ず用意する。
4. **クエリ本数の上限（項目 6）— 設計変更あり。** `query-count.test.ts` の `MAX_QUERIES = 14` は `prepare` の呼び出し回数。素直にデータセンター表を 1 本足すと 15 で落ちる。**上限を上げるのではなく uaSplit を畳む**: 現在 3 本（totals + byHuman + byBot）を、totals 1 本 + クラス別内訳 1 本（`ROW_NUMBER() OVER (PARTITION BY class ...)`、metricBreakdown と同じ形）の 2 本にする。データセンター表が増えても **13 本に減る**。
5. **判定の単一化を守らせるもの（項目 7・9）— 追加。** 既存の担保は `analytics.test.ts:325` の「`LIKE '${BOT_PREFIX}%'` はちょうど 1 回」だけで、これは UA 側しか守らない。データセンター判定にも同型の検査を足す。SQL 断片はパターン配列から生成し（手書きの LIKE 列を置かない）、「生成された断片の LIKE 数 == 配列長」を検査する。パターンに `'` `%` `_` を含めないことも検査する（定数のみなのでインジェクションは無いが、意図しない一致は起きる）。
6. **判定の三重定義を作らない（項目 3 の兄弟箇所）— 追加。** `isBotSummary`（visitor.ts:131）は src から未参照でテスト専用、SQL 側の BOT_MATCH と既に二重定義。ここに TS 版のデータセンター判定を足すと三重になる。新モジュールは SQL 断片を単一の情報源とし、TS 述語はテストが要求する分だけ同じ配列から導く。
7. **規約テストの除外マーカー（項目 2）— 実装時の注意。** `exempt = ['BOT_MATCH', 'MAX(id)']`（analytics.test.ts:313）は近傍 200/400 文字の粗い一致。BOT_MATCH の名前や配置を変えるならこのマーカーも同時に直す（直さないと uaSplit / eventBreakdowns が ${HUMAN_ONLY} を要求されて落ちる）。
8. **該当しなかった項目**: 5（キャッシュ・常駐化なし、順序は変わらない）、8（非同期の表示差し替えなし）、10（Swift の型グループ規定は site の TS に無い。判定は analytics.ts に足さず `src/lib/` の新モジュールへ出す）。

### 別タスク候補（このタスクではやらない）
