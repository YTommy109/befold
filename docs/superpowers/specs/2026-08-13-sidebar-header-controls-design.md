# サイドバーヘッダーのコントロール整理

<!-- derived-from ./2026-07-28-sidebar-git-status-design.md -->

## 背景

サイドバーヘッダー（`BefoldApp/befold/Viewer/SidebarHeaderView.swift:65-77`）には
現在 4 つのアイコンボタンが横一列に並んでいる。

| # | ボタン | 現在の位置 | ゲート |
| --- | --- | --- | --- |
| 1 | ソート順（フォルダー優先 / アルファベット順） | ヘッダー右 `:79-92` | なし |
| 2 | 不可視ファイル表示 | ヘッダー右 `:94-105` | なし |
| 3 | 変更されたファイルのみ表示 | ヘッダー右 `:109-121` | `FeatureGate.isSidebarGitStatusEnabled` |
| 4 | 名前フィルター | ヘッダー右 `:123-139` | なし |

TASK-409 で表示形式（ツリー / ドリルダウン）の切替に ⌃⌘T を割り当てたが、
この操作にはボタンが無い。ボタン化すると 5 個になる。

問題は 2 つある。

1. **密度**: 幅の狭いサイドバーで 5 個の等価なアイコンが並ぶと窮屈で、フォルダー名の
   表示幅とも競合する。
2. **系統のばらつき**: 「一覧の形」（ソート順・表示形式）と「何を出すか（絞り込み）」
   （不可視・変更のみ・名前）という性質の違う操作が同列に並んでおり、どれが何の仲間か
   読み取れない。

## 決定

<!-- constrained-by #背景 -->

ヘッダーの操作行を**左右に分割**し、常設 3 + オーバーフロー 1 の計 4 コントロールにする。

```text
┌────────────────────────────────┐
│ ⎇ ~/behold (main)              │  BaseDirectoryIndicator（変更なし）
│ [⎇] behold        [⚇][⚑][⋯]  │  操作行
└────────────────────────────────┘
   ↑左＝一覧の形     ↑右＝絞り込み＋その他
```

- **左群（新設）**: 表示形式トグル。`list.bullet.indent`（ツリー）/ `list.bullet`
  （ドリルダウン）をモードで出し分ける。既存の `eye` / `eye.slash`
  （`SidebarHeaderView.swift:98`）と同じ「状態をアイコンで表す」流儀に揃える。
- **右群**: 変更のみ（現状維持）、名前フィルター（現状維持）、⋯ オーバーフロー（新設）。
- **⋯ の中身**: ソート順（チェック付き 2 択）と不可視ファイル表示（チェック）。

表示形式を右群に入れないのは意図的な非対称である。絞り込みではないものを絞り込み群に
混ぜると、分割そのものが意味を失う。左に単独で置くことが系統の表明にあたる。

### 1 クリック層の根拠

常設に残すのは名前フィルター・表示形式・変更のみの 3 つ。ソート順と不可視ファイルを
畳む。ソート順はどのメニューにも項目が無い（`MainMenuBuilder+ViewMenu.swift` に該当なし）
ため、⋯ が唯一の入口になる。アイコンのみだった操作にラベルが付く分、可読性はむしろ上がる。
不可視ファイル（⌃⌘H）と表示形式（⌃⌘T）はメニュー項目があるので、畳んでもキーボードからは
1 手のまま。

## 状態の見え方

「今どれが効いているか」を 1 つのルールに統一する。

- 絞り込みが効いているボタンはアクセント色にする。対象は「変更のみ」「名前フィルター」
  「⋯」の 3 つ。
- **⋯ は、畳んだ絞り込み（不可視ファイル表示）が ON のときだけアクセント色**にする。
  これが無いと、畳んだ瞬間に「隠しファイルが出ている理由」がヘッダーから消え、一覧に
  `.DS_Store` が並ぶ説明が付かなくなる。
- ソート順はアクセント対象にしない。常にどちらかである以上「効いている / いない」が
  無く、同じ表現を使うと意味が濁る。⋯ 内のチェックマークだけで示す。
- 表示形式（左群）もアクセント対象にしない。アイコン自体がモードを表している。

## データフロー

<!-- constrained-by ./2026-07-28-sidebar-git-status-design.md -->

新しい経路を作らない。

- 表示形式ボタンは **⌃⌘T と同じ `AppDelegate.toggleSidebarTreeLayout` を通す**。
  ボタン専用の切替経路を足すと、メニュー経由とボタン経由で確定タイミングがずれる型を
  再生産する（`appendChunk` 抑止判定が TASK-318 → 329 → 339 と 3 連鎖した形）。
  送信点を 1 本に保つ。
- 真実の源は `SidebarDisplayPreference.layoutMode`（`App/SidebarDisplayPreference.swift:36`、
  永続・全ウィンドウ共有）のまま変えない。配布は既存の `GlobalDisplayBroadcaster` 経路。
- ゲート付きボタンは「変更のみ」と同型にする。`ViewerWindowAssembler.swift:157-168` の
  optional closure 注入（nil なら非表示）に倣い、ゲート値はビュー内で読まず composition
  root から渡す（`.swiftlint.yml` の custom rule `feature_gate_direct_reference` に沿う）。

### スコープ外

**ソート順の永続化は行わない。** 現状 `FileListModel.sortOrder`（`Viewer/FileListModel.swift:167`）
直書きでウィンドウごと・非永続である。⋯ へ移すのは配置変更であり、保存の有無は変えない。
ここを併せて変えると UserDefaults キー新設（移行・stale キー削除・3 ケーステスト）が
丸ごと入り、整理という目的からスコープが外れる。別タスクとして起票する。

## ファイル構成

- `Viewer/SidebarHeaderControls.swift`（新規）: 操作行の描画。`SidebarHeaderView.swift`
  は現在 140 行で、左右群・アクセント判定・オーバーフローメニューを足すと膨らむため、
  `file_length` を超える前に分ける。
- `Viewer/SidebarHeaderControlsModel.swift`（新規）: 表示するボタンの決定ロジック（下記）。
- 新規ファイルの追加後は `xcodegen generate` を実行する。

## テスト

SwiftUI ビューは自動テスト対象外という規約があるため、判定を純粋な値型へ出す。

`SidebarHeaderControlsModel` は入力
`(layoutMode, showHiddenFiles, showChangedFilesOnly, isFilterActive, isTreeLayoutAvailable, isChangedFilesOnlyAvailable)`
から、**左群・右群それぞれのボタン記述の配列**（SF Symbol 名・help のローカライズキー・
アクセント有無）を返す。ビューはそれを描くだけにする。

ユニットテストで次を固定する。

1. ゲート ON / OFF の**両方向**で、表示形式ボタンと変更のみボタンの有無が一致する
   （実ビルドではゲートが片側に固定されるため、注入点で両方向を見る）
2. 不可視ファイル ON のとき、かつそのときだけ ⋯ がアクセントになる
3. ソート順に応じてアイコンと ⋯ 内のチェック位置が切り替わる
4. 左群・右群の**並び順そのもの**を配列比較で固定する

4 は「決めたことに、破れたら落ちるものを付ける」に当たる。左右分割は doc コメントに
書くだけでは次のボタン追加で崩れるため、並びを配列で固定する。

## ⋯ に入れてよいものの制約

入れてよいのは「サイドバーの一覧の見え方に効く設定で、常設に値しないもの」だけ。
ファイル操作・ウィンドウ操作は入れない。何でも入る箱にすると、畳んだこと自体が
新しい散らかりになる。この制約は `SidebarHeaderControlsModel` の doc コメントに残す。

## 完了条件

1. ヘッダーが左群（表示形式）／右群（変更のみ・フィルター・⋯）に分かれ、ソート順と
   不可視ファイルが ⋯ 内に移っている
2. 表示形式ボタンは ⌃⌘T と同じ経路を通り、切替結果が全ウィンドウ・再起動後も一致する
3. ゲート OFF で表示形式ボタンと変更のみボタンがヘッダーから消える
4. 不可視ファイル ON のとき ⋯ がアクセント色になる
5. 上記 1〜4 が `SidebarHeaderControlsModel` のユニットテストで担保され、`swift test`
   が全通過する

## 未確認の前提

- ソート順ボタンの利用頻度は実測していない。⋯ へ畳む判断は「常にどちらかであり、
  一度決めたら変えにくい設定」という性質からの推定であり、使用ログに基づくものではない。
- アクセント色の適用が macOS のアクセシビリティ設定（色を弱める / コントラストを上げる）
  下で十分に判別できるかは未検証。実装時に「色以外の手掛かり」（⋯ 内のチェック）が
  併存していることで補う。
