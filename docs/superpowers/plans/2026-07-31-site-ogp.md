# 配布サイト OGP 対応 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

<!-- derived-from ../specs/2026-07-31-site-ogp-design.md -->

**Goal:** 配布サイト `/` を SNS に投稿したとき、専用の 1200×630 画像を持つ大判カードが表示されるようにする。

**Architecture:** OGP 画像は HTML テンプレートをヘッドレス Chrome で撮影した静的 PNG として
`site/public/images/ogp.png` にコミットし、`[assets]` バインディング経由で配信する。
メタタグは Hono JSX の `Landing` コンポーネントに追加し、`og:image` / `og:url` の絶対 URL は
ルートハンドラが渡すリクエスト origin から組み立てる（本番と staging で同じコードが正しく動く）。

**Tech Stack:** Cloudflare Workers / Hono 4 (JSX SSR) / TypeScript / Vitest 4 + `@cloudflare/vitest-pool-workers` / ヘッドレス Chrome

## Global Constraints

- 作業ディレクトリは `site/`。コマンドはすべて `site/` 直下で実行する。
- OGP 画像のサイズは **1200×630** 固定。
- 画像内コピー・`og:title`・`og:description` はすべて **英語**。
- `og:image` / `og:url` にホスト名をハードコードしない。必ずリクエストの origin から組み立てる。
- `og:title` は既存の `<title>` と、`og:description` は既存の `<meta name="description">` と
  **同一の文字列**にする。二重管理を避けるため定数へ切り出す。
- 既存の日本語コメントのトーン（「なぜ」を書く）に合わせる。
- コミットメッセージは Conventional Commits + 日本語。

```tsx
/** og:title / og:description を <title> / description と二重管理しないための定数。 */
const PAGE_TITLE = 'befold — File Viewer for macOS'
const PAGE_DESCRIPTION =
  'befold is a lightweight macOS viewer for reviewing the Markdown that terminal coding agents like Claude Code and Codex generate. Open any file from the CLI or with ⌘P — including git worktrees — and read Mermaid, Markdown, SVG, HTML and CSV with live reload.'

/**
 * 配布 LP。ダウンロードは計測用の /download 経由にする。
 *
 * origin を受け取るのは、OGP のクローラが絶対 URL しか解決できない一方で、
 * ホスト名をハードコードすると staging が本番の URL を指してしまうため。
 */
export const Landing: FC<{ origin: string }> = ({ origin }) => (
  <html lang="ja">
    <head>
      <meta charset="UTF-8" />
      <meta name="viewport" content="width=device-width, initial-scale=1.0" />
      <title>{PAGE_TITLE}</title>
      <meta name="description" content={PAGE_DESCRIPTION} />
      <link rel="canonical" href={`${origin}/`} />
      <meta property="og:type" content="website" />
      <meta property="og:site_name" content="befold" />
      <meta property="og:title" content={PAGE_TITLE} />
      <meta property="og:description" content={PAGE_DESCRIPTION} />
      <meta property="og:url" content={`${origin}/`} />
      <meta property="og:image" content={`${origin}/images/ogp.png`} />
      <meta property="og:image:width" content="1200" />
      <meta property="og:image:height" content="630" />
      <meta
        property="og:image:alt"
        content="befold — a macOS file viewer showing a rendered Mermaid diagram"
      />
      <meta name="twitter:card" content="summary_large_image" />
      <link rel="stylesheet" href="/style.css" />
    </head>
```

**仕様からの逸脱が 1 点ある。** 仕様のテスト 4「`/images/ogp.png` が 200 で返る」は、
`[assets]` バインディングの静的配信が `@cloudflare/vitest-pool-workers` 上で
再現される保証がなく、ユニットテストに置くと環境依存で不安定になる。
代わりに Task 1 Step 4 で PNG の寸法を、Task 3 Step 3 で実環境の 200 応答を確認する。
仕様が意図した「画像が本当に配信される」ことは、より確実な形で担保される。

代わりに仕様になかったテストを 1 件足した（`og:title` / `og:description` が
`<title>` / `description` と一致する）。定数へ切り出す設計が壊れたら気づけるようにするため。

**Placeholder scan:** なし。`<subdomain>` は Task 3 Step 1 の出力から埋める値であり、
実行時に判明する実在の値なので TBD とは異なる。

**Type consistency:** `Landing` は Task 2 で `FC<{ origin: string }>` になり、
呼び出しは同 Task Step 4 の `<Landing origin={...} />` のみ。他に呼び出し元はない
（`site/src/routes/public.tsx` L5 の import だけ）。
`PAGE_TITLE` / `PAGE_DESCRIPTION` は `landing.tsx` 内で定義・使用が閉じている。
