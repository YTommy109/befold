# ADR 0010: 新しいウィンドウの寸法はアプリ全体で 1 個にし、窓ごとの寸法はセッションに持たせる

- ステータス: Accepted
- 日付: 2026-09-01
- backlog decision: decision-10
- 関連タスク: TASK-583（TASK-74 の判断を上書きする）

## Context

### 現状（実測 / 2026-09-01 時点）

`WindowFrameStore` は 2 つの入れ物を持っていた。

| キー | 粒度 |
| --- | --- |
| `WindowFrames` | 正規化パス → `NSWindow.frameDescriptor` の辞書 |
| `WindowFrameLastUserAdjusted` | app-global の単一文字列 |

新しい窓の寸法は `initialFrameDescriptor(for:lastActivePathKey:)` が
「そのファイル自身の保存値 → 直近アクティブだったファイルの保存値 →
`WindowFrameLastUserAdjusted` → 既定値」の順で解決していた。

これに加えて、`ViewerWindowManager` が窓を開くたびに**解決結果をそのファイルの保存値として
書き戻して**いた。結果として、一度開いたファイルは以後ずっと第 1 段で止まり、
あとからユーザーが調整した寸法が届かなくなる。

利用者の defaults を実測したところ、`WindowFrames` は 104 件あり、
そのうち `WindowFrameLastUserAdjusted`（最後に調整した寸法）と一致するのは **1 件だけ**だった。
つまり過去に開いた 103 ファイルは、最後に調整した寸法とは違う大きさで開いていた。

利用者からは「ウィンドウサイズをうまく覚えてくれない。最後に調整した値がグローバルに
保存され、次にファイルを開くときに参照される仕様のつもりだった」と報告された。

### この判断が上書きするもの

ファイル単位の記憶は TASK-74（Done / 2026-07-19）で**意図的に導入した**もので、
きっかけは同じ利用者の指摘だった。

> ユーザー指摘: 複数ウィンドウを開いて再起動すると、両方とも同じウィンドウサイズで
> 復元される（`ViewerWindowController.lastWindowFrameKey` が全ウィンドウ共有の単一キーで
> あるため）。サイドバー開閉状態と同じ保存ロジックを再利用して解決する方針で本タスクに統合する。

つまり過去には app-global 単一キーだけの実装があり、それを捨ててファイル単位にした。
今回はその逆方向であり、**同じ人が両方の不満を述べている**。両立するには、
「新しく開くときの寸法」と「再起動時に各窓を戻す寸法」を別のものとして扱う必要がある。

## Decision

**2 つの関心を分け、それぞれ別の層に置く。**

| 関心 | 置き場 | 分類（ADR 0002） |
| --- | --- | --- |
| 新しい窓の出発点になる寸法 | `WindowFrameStore`（`WindowFrameLastUserAdjusted` 1 個） | アプリの好み |
| 再起動時に各窓を戻す寸法 | `SessionLayout.TabGroup.frame` | 窓の状態 |

ファイル単位の記憶（`WindowFrames`）は廃止する。

付随して次を決めた。

- **グローバル値を書く契機はリサイズの確定のみ**（`windowDidEndLiveResize`）。
  閉じたときには書かない。複数の窓を一括で閉じると `windowWillClose` の到達順は
  AppKit 任せで、どの窓の寸法が残るかを制御できないため。
- **`WindowFrameStore` に URL を引数に取る API を置かない。** 粒度を doc コメントではなく
  型の形で守る（ファイル単位で読む書き方がコンパイルできない）。
- **`WindowFrames` は移行しない。** 読み手が 0 になったキーとして
  `AppStores.retiredDisplayStateKeys` へ入れて削除する。104 件のうちどれを
  「アプリ全体で 1 個」の値に選ぶかに根拠が無く、選べば必ず 103 件を捨てることになる。
  現役の `WindowFrameLastUserAdjusted` はそのまま使うので、利用者が最後に調整した寸法は残る。

## Consequences

### 得られるもの

- 最後に調整した寸法が、次に開くファイルへ必ず届く（過去に開いたかどうかに依存しない）
- 再起動時は各窓が前回の寸法へ戻る（TASK-74 が解いた不満は再発しない）
- 寸法の記録が終了時の一括スナップショットに一本化され、窓を閉じる順序に依存しなくなる

### 失うもの

- **ファイルごとに違う寸法を覚える性質は無くなる。** 「この文書はいつも横長で開きたい」は
  表現できない。要望が出たら、文書の種別（PDF / Markdown 等）ごとの既定として
  別の軸で設計し直す——パス単位の辞書へ戻さない。
- 位置だけを動かして閉じた場合、その位置は次に開く窓へ引き継がれない
  （リサイズ確定でしか記録しないため）。再起動時の復元では位置も戻る。

### 破れたら落ちるもの

- `ViewerWindowManagerTests` の「別のファイルを開いても同じ寸法から始まる」——
  ファイル単位の記憶が復活すると落ちる
- `ViewerWindowControllerTests` の「ウィンドウを閉じたときにはフレームを通知しない」
- `SessionLayoutTests` の「絞り込んでも窓の寸法は保たれる」
- `RetiredDisplayStateKeysTests` の一覧ピン留め（`WindowFrames` を掃除対象から外すと落ちる）

## 追補（2026-09-06 / TASK-593.5）

粒度を「アプリ全体で 1 個」から**「窓の種別ごとに 1 個」**（`.viewer` / `.slide` の 2 値）へ広げた。

### 理由

スライド窓（`ViewerWindowKind.slide`）は画面共有・プロジェクターへ映すので 16:9 に寄せたく、
通常窓は文書を読む形にしたい。1 個しか持たないと、プレゼン用に広げた寸法が
`windowDidEndLiveResize` 経由で次に開く通常窓へそのまま漏れる。

### この決定を巻き戻していない理由

上の Context が退けたのは**ファイル単位**の記憶で、失敗の中身は「記憶の個数がファイル数だけ
増え、後からの調整が過去のファイルへ永久に届かない」ことだった（実測 104 件中、最後に調整した
寸法と一致するのは 1 件）。種別は**閉じた 2 値**で、同じ種別の窓を 1 回リサイズすれば次から必ず
それで開くため、この失敗モードは再現しない。ファイル単位の API を置かない規則は変えていない。

### 保存キー

通常窓は既存の `WindowFrameLastUserAdjusted` をそのまま読む（変えると利用者が今まで調整して
きた寸法が黙って失われる）。新設は `WindowFrameLastUserAdjustedSlide` の側だけで、
**種別をまたぐフォールバックはしない**——スライド窓が未調整のときに通常窓の値を借りると、
避けたい「文書用の寸法でプレゼンが始まる」が初回に起きる。

### 採らなかった案: 出力先（画面共有 / プロジェクター）で分ける

必要な比が今はどちらも 16:9 で差が小さい一方、アプリは出力先を判定できないため必ず手動の
切り替えになる。切り替え忘れが「意図しない比で映る」害になり、分けた分だけ悪くなる。
