# ADR 0011: 旧世代の配布経路（workers.dev / GitHub バイナリ配布）の停止条件を定める

- ステータス: Accepted
- 日付: 2026-09-04
- backlog decision: decision-11
- 関連タスク: TASK-489.1（親 TASK-489）
- ADR 0007 との関係: **更新（supersede ではない）**。ADR 0007 の決定 1 は
  「停止時期は定めない」で終わっており、その空白をこの ADR が埋める。0007 の
  他の決定（2〜6）はすべて有効なまま。

## Context

ADR 0007 は旧ホスト `befold.tommy109.workers.dev` の恒久併存を決め、停止条件を
「旧ホストの appcast を叩くクライアントがゼロになったこと。ただし観測できても
ゼロを保証できない」と書いたうえで、停止時期を定めなかった。GitHub Releases の
バイナリ配布についても `.github/workflows/release.yml` のコメントが
「移行期の後方互換とロールバックのために残す」とだけ書いている。

**どちらも「消せない」のではなく「消せる条件が書かれていない」状態だった。**
観測手段は TASK-489.5 / TASK-488.3 で用意され（`events.host` と `events.fallback`、
ダッシュボードの配信面）、数字は読めるようになった。読める数字を停止判断へ
つなぐ規則がこの ADR にあたる。

### どのバージョンがどこを見ているか（コード参照 + 実測）

フィード URL はバイナリに焼き込まれており、後から変更できない。切り替えた
コミットを追うと 3 世代に分かれる。

| バージョン範囲 | Sparkle のフィード URL | 切り替えたコミット |
|---|---|---|
| v1.10.0 以前 | GitHub の固定リリース `appcast` のアセット直リンク | — |
| v1.10.1 〜 v1.12.x | `https://befold.tommy109.workers.dev/appcast*.xml` | `b6e2ba33`（v1.10.1 に含まれる） |
| v1.13.0 以降 | `https://befold.degino.com/appcast*.xml` | `9a1ef1fc`（v1.13.0 に含まれる） |

D1 の実測（2026-09-04、`events.host` が入った 2026-08-16 以降の全期間）はこの
区分と一致する。旧ホストの `update_check` を出したのは `1.12.0` と
`1.12.3-dev.10` の 2 件だけで、`befold.degino.com` 側の `update_check` 118 件は
すべて v1.13.0 以降のバージョンだった。**新旧の境界はバージョンで完全に割れており、
「新ドメインへ移った人」と「旧ホストに残っている人」が混ざる区間は無い。**

### 現行 appcast の enclosure は全部 degino を指している（重要）

実測（2026-09-04）:

```text
curl -s https://befold.degino.com/appcast.xml | grep -o 'url="[^"]*"'
  → 3 件すべて https://befold.degino.com/dl/...
（appcast-develop.xml も同じく 3 件すべて degino）
```

`generate_appcast` が保持するエントリは 3 件で、そのすべてが新ドメインの `/dl/` を
指す。**旧ホストの `/appcast*.xml` を叩いた v1.12.x のクライアントも、返ってくる
enclosure は degino の `/dl/` になる。**同一 Worker が両ホストで同じ内容を返すため
（ADR 0007 の決定 1）、ホスト名だけが旧で中身は新しい。

これは ADR 0007 が書いた「配信済み appcast の enclosure URL は変更できない」という
制約が、**現在は実効的に消えている**ことを意味する。Sparkle は更新のたびに
フィードを取り直すので、クライアント側に古い enclosure は残らない。実測でも
旧ホストの `download`（`/dl/`）は**全期間で 0 件**である。

したがって旧ホストの `/appcast*.xml` と `/dl/*` は**別々に判断できる**。ADR 0007 は
この 2 つを 1 つの「旧ホスト維持」に畳んでいたが、それは enclosure が旧ホストを
指していた時点の前提に基づく。

### 停止判断に使える指標と、その限界

| 指標 | 取り方 | 限界 |
|---|---|---|
| 旧ホストの `update_check` | `events` の `host='befold.tommy109.workers.dev' AND kind='update_check'` | `host` 列は 2026-08-16 以降。それ以前は NULL で切り分け不能 |
| 旧ホストの `download` | 同上 `kind='download'` | 同上 |
| GitHub 直の appcast | `appcast` リリースのアセットの `download_count`（GitHub Releases API） | **リリースのたびに 0 に戻る。** `release.yml` が `gh release upload --clobber` で置き換えるため、カウンタは「前回リリース以降」しか表さない |
| GitHub へのフォールバック | `events` の `kind='github_fallback'`、`fallback` が `appcast` / `dmg` / `release-api` | `dmg-invalid` は配布対象でないパスへの要求なので数えない（`site/README.md`）。appcast のフォールバックは 300 秒キャッシュのぶん過小に出る |
| GitHub Releases のアセット取得 | 各リリースのアセットの `download_count` | Worker の `/dl/` フォールバックによる 302 の先も同じカウンタを増やすため、**直接アクセス分だけを取り出せない**。実測 2026-09-04 で合計 81 件 |

**ゼロ判定はロボットの上に乗せない。** ADR 0008 のとおり `as_org` による
データセンター判定を併用し、人間分とロボット分を分けて読む（実測 2026-09-04 でも
旧ホストの `legacy_redirect` 24 件の大半は Googlebot / Meta-ExternalAgent /
facebookexternalhit だった）。

### 前提の裏付け

| 前提 | 裏付け |
|---|---|
| フィード URL の 3 世代とその境界バージョン | コード参照（`git log -S` によるコミット特定）+ 実測（D1 の `app_version` × `host`） |
| 現行 appcast の enclosure が全て degino | 実測（上記 curl、2026-09-04） |
| 旧ホストの `/dl/` が全期間 0 件 | 実測（D1、`host` 列導入以降の全期間） |
| GitHub appcast アセットのカウンタがリリースごとに 0 に戻る | コード参照（`.github/workflows/release.yml` の `gh release upload --clobber`）+ 実測（`updated_at` が直近リリース日、`download_count` が 0） |
| GitHub のアセット取得数が Worker フォールバック分と混ざる | コード参照（`site/src/routes/public.tsx` の `/dl/` が GitHub アセットへ 302 する） |
| `host` 列より前の期間を遡って分類できない | コード参照（`site/schema/schema.sql` に列が無かった期間の行は NULL） |

## Decision

停止対象を **4 つに分け、別々の条件を持たせる**。ひとつの「停止」に畳まない。
リスクの大きさが桁違いに違う。

すべての条件は次の共通形で書く。**「ゼロが続いたら止める」ではなく、
「ゼロが続いたうえで、切れても構わないと判断する版を明示して止める」**
（ゼロは観測できてもゼロを保証しないため。ADR 0007 の指摘は正しい）。

```text
条件 = 指標が人間分ゼロ + 継続期間 + 切り捨てを受け入れるバージョン範囲の明示
```

### 1. 新規リリースでの GitHub Releases への DMG 添付をやめる条件

**条件**: 次の 2 つを同時に満たすこと。

- `kind='github_fallback' AND fallback='dmg'` の**人間分**が 90 日連続でゼロ
- 現行 appcast（stable / develop）の全 enclosure が R2 に存在する

**切れる対象**: なし。既存のアセットは残るため、過去に配信された更新経路は
どれも壊れない。止まるのは「R2 への put が失敗した新リリースの退避先」だけで、
これは `release.yml` が put 失敗をジョブ失敗として扱うことで別に担保されている。

**90 日と短くしている理由**: 唯一の失敗モードが「R2 から成果物が消えたときに
GitHub へ落ちられない」であり、これは配信側の事故であって出荷済みクライアントの
バージョンに依存しない。ユーザーの起動間隔を待つ必要が無いので、他の条件より短くてよい。

### 2. 固定リリース `appcast` への appcast アップロードをやめる条件

**条件**: 次の 3 つを同時に満たすこと。

- `appcast` リリースの `appcast.xml` / `appcast-develop.xml` の `download_count` が、
  **リリースを 3 回またいで**いずれも 0（カウンタがリリースごとに 0 に戻るため、
  期間ではなくリリース回数で数える。これがこの指標で書ける最も強い形である）
- `release.yml` が `gh release download appcast` を**入力として使わなくなっている**
  （入力を R2 へ移す先行作業。これが済むまで条件を満たしても止められない）
- 最後の判定から 180 日以上が経過している（リリース間隔が短い時期に 3 回を
  消化してしまうのを防ぐ）

**切れる対象**: **v1.10.0 以前**。これらのクライアントは GitHub の appcast を直接
見ており、止めた時点で自動更新が永久に止まる（サイトからの手動再インストール以外の
復帰経路が無い）。この範囲を切り捨てることを決定として受け入れる。

**判断の根拠**: v1.10.0 は 2026 年前半のリリースで、その後 v1.17 まで 7 世代の
stable を出している。カウンタが 0 に戻る指標である以上「かつて一度も無かった」は
証明できないが、**3 回のリリースをまたいで 0 という観測は「今この瞬間に使っている
人がいない」の最も強い近似**である。

### 3. 過去のリリースアセット（DMG）を削除する条件

**条件**: **原則として削除しない。**

削除してよいのは、次のすべてを満たすタグのアセットに限る。

- そのタグが現行 appcast（stable / develop）の enclosure に含まれていない
- そのタグの成果物が R2 に存在する（＝削除しても `/dl/` は R2 から返せる）
- `kind='github_fallback' AND fallback='dmg'` の人間分が 180 日連続でゼロ

**切れる対象**: 原則どおり削除しない限り、なし。

**「原則削除しない」を結論にする理由**: 得られるものが GitHub のストレージだけで、
失うものが「R2 に無い版を掘り出す最後の手段」だから。この非対称は継続期間を
延ばしても変わらない。削除は**要求が発生したときに**上の条件で個別に判断する
（一括削除のワークフローを作らない）。

### 4. workers.dev ホストを停止する条件

ADR 0007 の決定 1 が言う「旧ホスト維持」を、`/appcast*.xml` と `/dl/*` の
**2 つに分けて**扱う。現行 appcast の enclosure が全て degino を指しているため
（Context 参照）、この 2 つはもう連動しない。

#### 4a. 旧ホストの `/dl/*` を止める条件

**条件**: `host='befold.tommy109.workers.dev' AND kind='download'` が
**人間・ロボットとも 90 日連続でゼロ**（実測 2026-09-04 時点で全期間 0 件）。

期間を 4b と揃えてある。**4b は 4a の充足を要求するので、4a を長くすると
4b の期間指定が意味を失う**（長いほうに引きずられる）。4a のリスクは
「原理上到達できない経路を止める」で実質ゼロなので、短いほうへ揃える。

**切れる対象**: なし。現行 appcast の enclosure に旧ホストは 1 件も現れないため、
この経路を通るクライアントは原理上存在しない。ゼロは観測結果であると同時に
構造から導かれる。

#### 4b. 旧ホストの `/appcast*.xml` を止める（＝ `workers_dev = false` にする）条件

**条件**: 次の 2 つを同時に満たすこと。

- `host='befold.tommy109.workers.dev' AND kind='update_check'` の**人間分**が
  **90 日連続**でゼロ
- 4a の条件を満たしている

**切れる対象**: **v1.10.1 〜 v1.12.x**。止めた時点でこの範囲の自動更新が永久に
止まる。

**90 日という長さの理由**: 切り捨てる母集団が小さく、かつ 90 日を超えて
観測されない使い方では自動更新そのものが役に立っていないため。

母集団の実測（2026-09-04、GitHub Releases API のアセット `download_count`）:
この世代にあたる v1.10.1 〜 v1.12.3 の 11 リリースで**合計 19 件**（最大は
v1.11.6 の 5 件）。1 人が追随すれば各リリースで 1 ずつ増える数字なので、
実人数は数人規模になる。なおこの数字は Worker の `/dl/` フォールバック分と
混ざっているため、直接ダウンロードした人数はこれより少ない。

**当初この節は 365 日としていたが、短くした。** 365 日の根拠は「月に一度しか
開かないユーザーは 30 日の窓では観測されない」というもので、観測の性質としては
正しい。しかし**そこまで起動間隔が空くユーザーにとって、自動更新は既に機能を
果たしていない**（起動しない限りチェックも更新も走らない）。観測されない人を
守るために経路を維持するという理屈は、その人が経路から利益を得ている場合にのみ
成立する。90 日開いていない人はその条件を満たさない。

実測（2026-09-04）では最後の `update_check` が 2026-08-21 で 14 日間ゼロ。
条件は未達で、**最短の充足日は 2026-11-19**（以降に新たな `update_check` が
無ければ）。

**`workers_dev = false` は最後に触る。** `site/wrangler.toml` はこのフラグを
「消してはならない」と明記しており、`routes` を書いた時点で次回デプロイで
`false` と推論される仕様がある。フラグを外すのは 4a・4b の両方が揃ってからで、
それまでは明示指定を残す。

### 5. 判定は四半期に 1 回、タスクで行う

条件を満たしたかの判定は TASK-489.4（条件を満たした旧世代の配布経路を実際に
停止する）で行い、そのタスクの Notes に**判定日と各指標の実測値**を残す。条件を
満たさなかった場合もタスクは閉じず、次回の判定日を Notes に書いて To Do のまま戻す。

判定の間隔は最短の条件（90 日）に合わせる。年 1 回にすると、90 日で満たした
条件が最大 1 年寝ることになり、期間を短くした意味が消える。

「気づいたときに見る」形にしない。この種の条件は、満たされた瞬間に誰かが
気づくものではないため、判定の場所を決めておかないと永久に判定されない
（それが ADR 0007 の決定 1 に起きたことである）。

## Consequences

### 得るもの

- 「消せる条件を観測できていない」状態が終わり、4 つの経路それぞれについて
  次に何を見れば判定できるかが決まる。
- 旧ホストの `/dl/` が構造上もう使われないことが記録され、`/appcast*.xml` と
  切り離して先に止められるようになる（ADR 0007 の時点では見えなかった）。
- 切り捨てるバージョン範囲が条件ごとに明示されるため、停止の判断が
  「たぶん誰もいない」ではなく「v1.12.x 以下を切る」という形で下せる。

### 受け入れるコスト

- **どの条件も「ゼロを保証」しない。** 観測されない利用者を切ることを、
  バージョン範囲を明示したうえで受け入れるという形にしている。ADR 0007 の
  指摘を解消したのではなく、判断として引き受けた。
- 条件 2 の指標（GitHub の `download_count`）はリリースごとにリセットされる。
  期間ではなくリリース回数で数えるという歪んだ形になっており、リリース頻度が
  変われば意味も変わる。より良い指標が手に入ったら条件 2 を書き直すこと。
- `host` 列より前（2026-08-16 以前）の期間は遡って分類できない。すべての
  継続期間は 2026-08-16 以降でしか数えられない。
- 判定を四半期 1 回のタスクに預けるため、条件を満たしてから実際に止まるまでに
  最大 90 日の遅れが出る。止めることに緊急性が無いので許容する。
- **決定 4b は「90 日開いた利用者は自動更新から利益を得ていない」という判断に
  乗っている。** これは観測ではなく解釈であり、反例（年に数回開くが開いたときは
  更新されてほしい利用者）を否定できない。母集団が数人規模であることと合わせて
  受け入れる。

### 破れたら落ちるもの

| 決定 | 担保 |
|---|---|
| 4b（`workers_dev` を最後に触る） | `site/wrangler.toml` に `workers_dev = true` が残ることを検査する既存のテスト（ADR 0007 の担保をそのまま使う）。条件を満たす前にフラグを外すとこれが落ちる |
| 4a（旧ホストの `/dl/` は enclosure に現れない） | 旧ホストの `/dl/<tag>/<file>` が 200 を返す既存のテスト（ADR 0007 決定 2 の担保）。止めるときはこのテストを消す必要があり、消すことが判断の記録になる |
| 5（判定の場所） | TASK-489.4 を To Do のまま残す。条件を満たさなかった判定でも閉じない |
| 3（原則削除しない） | 一括削除のワークフローやスクリプトを作らない。作らないことが担保になる |

## 未確定事項

- 条件 2 の先行作業（`release.yml` が `gh release download appcast` を入力として
  使うのをやめ、R2 を入力にする）は起票していない。条件 2 の判定が近づいた時点で
  起票する。
- 条件 1 を満たしたあと、GitHub Release そのもの（DMG を添付しない、ノートだけの
  リリース）を作り続けるかは決めていない。ソースリポジトリとしてのタグの記録には
  価値があるため、添付の停止と Release 作成の停止は別の判断になる。
